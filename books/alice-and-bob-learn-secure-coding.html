The book in one page

Security is not a feature you add at the end — it is a set of small habits applied at every step: validate input, encode output, give the least privilege, protect secrets, log what happens, and keep everything patched.

Habit 1
Never trust data. Anything from a user, a partner API, or even your own database is input and must be validated.
Habit 2
Data ≠ code. Encode output so the browser shows text instead of executing it (stops XSS).
Habit 3
Least privilege. Every user, service and process gets only the access it needs — nothing more.
Habit 4
Allowlists, not blocklists. Say what is allowed; don’t chase every bad thing that exists.
Habit 5
Secrets stay secret. No passwords or keys in code, config files or chat. Use a secret manager.
Habit 6
Assume breach. Log, monitor, alert — and have a plan for the day something goes wrong.
Habit 7
Fail closed. When in doubt, deny access and break the feature, not the security.
Habit 8
Keep it simple. Complexity is the enemy of security: fewer features, fewer dependencies, fewer bugs.
The mental model

Alice and Bob are ordinary developers, not security experts. The book’s promise: you do not need to be a hacker to write safe code — you need a checklist, good defaults, and the humility to assume you will make mistakes.

Chapter 1 · Introductory Security Fundamentals

The vocabulary and mindset: what security actually means, which rules always apply, and which laws and standards you may be bound by.

Key points, in simple terms

  • Assume every other system and all data are insecure. You cannot control the other side — validate what arrives.
  • CIA triad — the three things you protect: Confidentiality (only the right people can see it), Integrity (nobody changed it), Availability (it works when needed).
  • Least privilege — give people, services and code the minimum access needed to do the job, and take it away when it is no longer needed.
  • Secure defaults / paved roads — make the safe way the easy way. If the secure option is the hard option, developers will avoid it.
  • Assume breach — design as if an attacker is already inside: segment networks, log everything, and plan for failure instead of being surprised by it.
  • Zero Trust — “never trust, always verify”; being inside the corporate network is not a permission slip.
  • Defense in depth — several independent layers (validation, encoding, WAF, least privilege) so one mistake is not fatal.
  • Supply chain security — you are responsible for every library, container and tool you pull in.
  • Security by obscurity — hiding things (secret URLs, weird port numbers) is the weakest control; use it only as an extra layer, never alone.
  • Attack surface reduction — every open port, API, feature and account is somewhere to be attacked. Turn off what you don’t need.
  • Usable security — if security is annoying, people work around it, and the workaround is usually worse.
  • Fail closed / fail safe — on error, deny. Then roll back the change that caused the problem.
  • Compliance is a floor, not a ceiling — the chapter walks through GDPR, PCI DSS, HIPAA, NIST, ISO 27001, DORA, FISMA, CCPA, NY DFS: they tell you what is mandatory, not what is enough.
  • Framework thinking — OWASP Top 10, OWASP ASVS and SAMM, NIST SSDF and BSIMM give you ready-made checklists.
  • Learn from mistakes and share them — blameless post-mortems make the whole industry safer.
  • Backward compatibility is risky — old protocols, old ciphers and old clients keep weak security alive.
  • Threat modeling — before building, ask “how could this be attacked?” and write down the answer.
  • Patching is hard and fixes create new bugs — so retest every fix; a fix for one vulnerability often opens another.

Chapter 2 · Beginning

The starter kit of secure coding: input validation, output encoding, parameterized queries, authentication and authorization, sessions, secrets, HTTPS, security headers and cookies.

The core defences

  • Follow a secure SDLC — security activities in every phase (this is Part III of the book, in detail).
  • Use a modern framework and switch on its security features — they already ship CSRF tokens, output encoding and secure sessions. Don’t rebuild them badly.
  • Input validation — check type, length, format and range. Prefer allowlists. Validate on the server, always, even when the client already did.
  • Output encoding — the context decides the encoding: HTML context needs HTML entities, JavaScript context needs JavaScript escaping, and so on. Get it wrong and the browser executes your data as code (XSS).
  • Parameterized queries / ORMs — never build SQL by gluing strings; let the driver separate the query from the data (stops SQL injection).
  • Authentication (AuthN) — “who are you?”. Use proven identity systems (OAuth, OIDC, SSO), MFA, strong password hashing, and rate-limited login.
  • Authorization (AuthZ) — “what may you do?”. Check it on every request, server-side, including object-level checks (can this user touch this record?).
  • Access control models — MAC (classification labels), DAC (owner decides), RBAC (by role), rule-based (dynamic rules); implemented with ACLs, group policies, and factors like passwords, PINs, tokens and biometrics.
  • Session management — long random session IDs, rotate the ID at login, time out idle sessions, and destroy the session on logout.
  • Secret management — API keys, passwords and private keys go in a secret manager or environment variables, never in git, never in the front end.
  • Password management — hash with bcrypt/scrypt/Argon2 and a salt, check against breached-password lists, allow long passphrases, offer MFA and passkeys.
  • Communication security — HTTPS/TLS everywhere (HSTS), strong ciphers, no downgrade, and certificate validation turned on.
  • Protect sensitive data — classify it, encrypt it in transit and at rest, don’t log it, don’t cache it, don’t put it in URLs or hidden fields, and delete it when retention allows.
Input validation & output encoding — the PHP example from the book (Chapter 2)book code
<?php
// get “name” from the form, then validate it before use
$name = validate_input($_POST["name"]);

function validate_input($data) {
  $data = trim($data);             // trim off spaces and tabs
  $data = stripslashes($data);     // remove backslashes
  $data = htmlspecialchars($data); // convert special characters (output encoding)
  return $data;                    // return safe-to-use data
}
?>
Why both?

Validation protects you (the app) from bad data. Encoding protects the browser from data that pretends to be code. The book is explicit: you need both, and the browser context (HTML, attribute, JavaScript, CSS, URL) decides which encoding is correct.

Secure cookies and error handling

  • Cookie flags: Secure (HTTPS only), HttpOnly (JavaScript cannot read it), SameSite=Lax/Strict (blocks cross-site sending), a tight Path and a short expiry.
  • Error handling: show users a generic message, log the details internally, never leak stack traces, SQL, file paths or version numbers. And when an error happens in a security check — deny.
A session cookie that is hard to stealsafe
Set-Cookie: sid=8f2c…long-random…; HttpOnly; Secure; SameSite=Lax;
            Path=/; Max-Age=1800

Parameters vs string-building (the injection fix)

Don’t build queries by concatenationvulnerable
const sql =
  "SELECT * FROM users WHERE email = '"
  + req.body.email + "'";
db.query(sql);   // input becomes code
Let the driver keep data as datasafe
db.query(
  "SELECT * FROM users WHERE email = ?",
  [req.body.email]
);   // parameterized

Chapter 3 · Improving

Level two: databases, files, memory, privacy, logging, cryptography and type systems — the places where “it works” is not the same as “it is safe”.

  • Database security — least-privilege roles (read-only where possible), long unique service-account passwords, encryption in transit and at rest, MFA for DB users, no production data in test environments, no copying data out of the database, monitoring and backups.
  • File management & uploads — restrict file types, verify the real type from the file header (not the extension), scan for malware, rename the file, never let the user choose the path, store files outside the web root, and make sure the storage server cannot execute them.
  • Your source code — it is a valuable asset. Keep it in access-controlled repos with reviews and signed commits.
  • Memory management — buffer, stack, string and integer overflows; over-reads; use-after-free; uninitialised variables; memory leaks. Prefer memory-safe languages, bounds checks, safer string functions, DEP/ASLR/stack canaries, and fuzzing.
  • (De)serialization — never deserialize objects from an untrusted source; that is how you get remote code execution instead of “data”.
  • Privacy — know what counts as PII/sensitive data, collect only what you need, get consent, honour retention and deletion, and log access to sensitive records.
  • Errors — fail closed, use a global error handler, never echo internals to the user.
  • Logging, monitoring, alerting — log every security-relevant event (logins, failures, permission denials, admin actions) with UTC timestamp, user, source IP and action; never log secrets or PII; alert on anomalies.
  • Locking resources — stop two requests from corrupting the same record at the same time (race conditions).
  • Cryptographic practices — use the vetted libraries and FIPS/NIST guidance, never invent your own crypto, never reuse an IV/nonce, and don’t store the key next to the data.
  • Strongly typed vs weakly typed languages — strong, static typing catches whole classes of bugs at compile time (type confusion, accidental comparisons, implicit conversions).
  • Domain-driven development & memory-safe languages — model the business rules explicitly so logic errors are visible, and choose languages where the compiler/runtime handles memory for you.

What a logged security event should contain

Log the event, not the secretsafe
{
  "ts": "2025-03-02T09:14:07Z",     // always UTC
  "event": "login_failed",
  "user": "alice@example.com",

Takeaway from the overflow figures

An overflow is not “a long string”. It is your data overwriting your program’s instructions. That is why the book recommends bounds checks, safer string functions, non-executable stacks (DEP), ASLR, and memory-safe languages first.

Chapter 4 · Achieving

How design decisions — dependencies, defaults, allowlists, configurations, code signing, privilege handling — decide most of your security before a single bug is written.

  • Secure design, and “how much is enough?” — weigh the risk: how sensitive is the data, who are your adversaries (script kiddies or nation-states), what does regulation require, what can the team realistically sustain?
  • Dependency & supply chain — know every component, check for known CVEs, use trusted registries, pin and lock versions, monitor continuously, and remember the chain includes your IDE, repo, CI/CD, package mirrors and third-party APIs.
  • Secure defaults for users — MFA offered (and mandatory for important systems), breach-password checks, backup codes, “last login” and “logged-in devices” views, account-recovery that can’t be abused.
  • Secure defaults for developers — secret-management policy, cloud security posture checks, SAST when code is committed, one-page how-tos, self-service, IDE plugins, automated checks, a unified stack and real training.
  • Readable and auditable code — naming conventions, security-relevant comments, simple logic, peer review, licensing compliance, refactoring, diagrams, and paying down technical debt.
  • Important functions belong on trusted systems — price calculation, privilege checks, signing and logging should never happen on the client or on an untrusted device.
  • Allowlists beat blocklists — blocklists are endless and trivially bypassed; an allowlist of what is valid is short and testable (e.g. names need letters, spaces, apostrophes, hyphens — not < or >).
  • Secure configurations — change default accounts and passwords, disable unused services and HTTP verbs, turn off directory listing and verbose errors, and keep production and development configurations separate.
  • Hostname validation — when you call out to a host, verify the certificate matches the hostname you intended (prevents redirection and man-in-the-middle).
  • Reusable code — build shared, reviewed, versioned, well-governed libraries so the safe way is the default for everyone.
  • Safe system calls — avoid passing user input to a shell; use argument lists, not command strings.
  • Comments and documentation — explain why a security control exists, keep docs short and current, and include diagrams.
  • Verification of user consent — collect data only for stated purposes, record consent, and re-ask when the purpose changes (including using data to train AI).
  • Integrity checks, code signing, immutable builds — sign releases, verify checksums, and make build artifacts immutable so nobody can swap them.
  • Avoiding brute force — rate limits, account lockouts with care, CAPTCHAs, exponential backoff, and monitoring for credential stuffing.
  • Security controls come in three flavours — physical (locks, doors), technical (software enforcement) and administrative (policies, procedures, training).
  • Handling elevated privileges — use just-in-time admin access, separate admin accounts, approval trails, and log everything an admin does.
  • Security maintenance & technical debt — patch, scan, review, and budget time to fix the “we’ll do it later” list, because attackers read your backlog too.
Safe system calls — no shell, no surprisessafe
# avoid: user input inside a shell string
os.system("ping -c 1 " + host)          # host = "8.8.8.8; rm -rf /"

# prefer: argument list, shell disabled, input validated first
subprocess.run(["ping", "-c", "1", host], shell=False, check=True)

Chapter 5 · Technology-Specific Secure Coding

The same principles, re-tuned for APIs, mobile apps, WebSockets, serverless and IoT — because each platform has its own favourite way to bite you.

APIs

  • Threat model first; put every API behind a gateway; add authorization beyond authentication (per endpoint, per object, per function).
  • Use proven auth (OAuth 2 / JWT done correctly), and never roll your own token format.
  • Rate-limit and quota everything: requests per client, payload size, records per page, file descriptors, connections.
  • Validate and strongly type parameters, encrypt requests and responses, avoid verbose errors, decommission old API versions properly, and block unused HTTP verbs.
  • Separate API keys per app, rotate them, and protect against SSRF (server-side request forgery) by allowlisting outbound destinations.

Mobile apps

  • Assume the app will be decompiled: no secrets, no logic you rely on, no keys inside the binary.
  • Store as little as possible on the device; never keep the encryption key beside the encrypted data; auto-delete local data.
  • Long-lived mobile sessions need remote wipe, remote logout, automatic timeout, tokens instead of device identifiers.
  • Ask only for the permissions you truly need, disable autocomplete/copy-paste for sensitive fields, and protect backups, screenshots and cached images.

WebSockets

  • Use wss://, validate the Origin of the handshake, re-check authentication during the session, rate-limit messages and cap payload size.
  • Don’t tunnel arbitrary traffic through the socket, and don’t trust a connection just because it stayed open.

Serverless

  • Each function gets its own minimal permissions; one function should do one thing.
  • Put it behind a gateway, validate inputs per function, set timeouts and memory limits, and watch for event-injection and denial-of-wallet costs.

IoT

  • Physical security matters; segment the network; ship a firmware-update plan before you ship the device.
  • No default passwords, unique credentials per device, protect the mobile app that controls it, and monitor devices like any other asset.

Chapter 7 · Popular Frameworks

Frameworks already contain the security features — the job is to switch them on, keep them updated, and not undo them.

  • Express — helmet for headers, rate limiting, body-size limits, no eval, validate with a schema library, handle errors centrally, don’t leak stack traces.
  • React — JSX escapes by default; dangerouslySetInnerHTML is named that way for a reason; never build javascript: URLs from user input; sanitize with DOMPurify when you must render HTML.
  • Angular — the built-in sanitizer plus DOMSanitizer; avoid bypassSecurityTrust* unless the value is genuinely trusted; use the HTTP client’s XSRF support.
  • jQuery — legacy risk: .html(), .append() with strings and old plugins are XSS vectors; prefer .text() and keep the library patched.
  • Vue.js — {{ }} escapes automatically, never use v-html with untrusted data, sanitize URLs, don’t render <script>, and use v-if over v-show for sensitive content.
  • .NET (Core) — built-in identity, anti-forgery tokens, data protection API, role-based checks, security headers helper, model-binding allowlists.
  • Ruby on Rails — strong parameters, CSRF tokens by default, html_escape/sanitize, avoid html_safe, use ActiveRecord, Brakeman for static analysis, system with argument arrays, secure session store.
  • Spring / Spring Boot — Spring Security for authN/authZ, CSRF protection and headers on by default, PasswordEncoder for hashing, JDBC/JPA for queries, method-level @PreAuthorize.
  • Flask — Jinja2 autoescapes, Flask-WTF CSRF protection, Flask-Login/Flask-Security for sessions, parameterized queries, flask.escape, Flask-SSLify for HTTPS.
The pattern across all frameworks

Every framework gives you (1) automatic output escaping, (2) CSRF protection, (3) a password hasher, (4) session handling, (5) security headers. Your job is to not bypass them — the dangerous functions are the ones with names like raw, safe, html, bypass, dangerously, eval.

Chapter 9 · Requirements

Security starts in the kick-off meeting: put it in the requirements and in the schedule, or it will not exist.

  • Invite a security representative to the project kick-off and record which security activities the project will do.
  • Write security requirements next to functional ones (“all traffic over TLS 1.2+”, “MFA for admin accounts”, “audit log retained 1 year”).
  • Estimate and schedule the security work: threat modeling, code review, scanning, pen test, remediation time.
  • Agree the compliance obligations up front (privacy, retention, data residency).

Chapter 10 · Design

Threat modeling is structured evil brainstorming — and it is cheapest to do with a whiteboard, not a production incident.

  • Threat model the architecture: what are we building, what can go wrong, what are we going to do about it, did we do a good job?
  • Draw the architecture, follow the data flows (where does sensitive data enter, get stored, get displayed, leave?), and mark the trust boundaries.
  • Apply secure design patterns and concepts (least privilege, separation of duties, fail-safe defaults, economy of mechanism).
  • Write security user stories — “As a security-savvy user I want my data protected from XSS so that…” — so security has acceptance criteria.
  • Document the mitigations you agreed, assign owners, set deadlines, and re-run the threat model when the design changes.

Chapter 11 · Coding

The daily work: trained people, reviewed code, and automated guardrails that catch the boring mistakes.

  • Training — for the organization (a programme, not a one-off video) and for individuals (this book, OWASP, hands-on labs).
  • Code review — a second pair of eyes, with a security checklist, focused on new and changed code.
  • Static analysis (SAST) — 1st-generation (pattern matching) and 2nd-generation (data-flow/semantic) tools; both have a place, both need triage.
  • Secure guardrails — pre-commit hooks, CI checks, IDE plugins with red squiggly lines, and templates that start secure.
  • Software composition analysis (SCA) — know your dependencies and their vulnerabilities; decide deliberately whether to update, patch or replace.
  • Secret scanning — catch keys before (or right after) they reach the repo, then rotate them.
  • Dynamic testing (DAST) — scan the running application, not just the source.

Chapter 12 · Testing

Testing is where you find out that the design was optimistic. Mix automated breadth with human depth, and act on the results.

  • Coverage and depth — decided by risk: sensitive, internet-facing, money-handling code gets the deepest testing.
  • Infrastructure scanning — hosts, containers, cloud configuration; test in environments that mirror production, but never with production data.
  • Manual testing / pen testing — humans find business-logic and chained bugs that scanners cannot.
  • Automated testing — SAST, DAST, IAST, SCA and secret scanning wired into CI.
  • Fuzzing — throw malformed and random input at every input to find crashes and overflows.
  • IAST — instruments the running app for high-signal, low-false-positive results (expensive, mostly used by mature/bank-grade programmes).
  • Bug bounty programmes — powerful but conditional: you need a fast triage process, a budget, and no “we’ll fix it next year” list.
  • Test results must be actionable — put findings where developers already work (ticket tracker / CI), with reproduction steps, severity and a fix suggestion. Never hide or falsely close findings.

Chapter 13 · Release & Deployment

The release pipeline is the last gate: sign what you ship, verify what you deploy, and keep humans in the loop.

  • Digitally sign releases and packages; verify checksums and provenance.
  • Pull dependencies only from trusted repositories, and run SCA on every build.
  • Protect the pipeline: reviews for configuration changes, MFA for CI/CD users, more than one person required to publish, and strictly limited access to build tooling.
  • Store secrets in the CI/CD secret store — never in build logs or environment files committed to the repo.
  • Deploy immutable, reproducible artifacts, and keep an auditable record of what went out and when.

Chapter 14 · Maintenance

Most of a system’s life happens after launch — that is where patching, monitoring and legacy systems decide whether you stay safe.

  • Patch and update continuously — dependencies, frameworks, runtimes, OS, containers.
  • Observability — logs, metrics and traces, so you can see attacks and outages before customers report them.
  • WAFs and virtual patching — a compensating control at the edge while the real fix is written (it buys time, not safety).
  • CDNs — absorb load and DDoS traffic, and serve cached content closer to users.
  • RASP / runtime protection — watch behaviour inside the app and block what looks wrong.
  • Legacy systems — inventory them, isolate them, and plan their retirement; unreachable, unpatched boxes are the classic way in.
  • Incident response — have a plan, follow “need to know”, tell the security team early, don’t play the hero, and log everything you do during the incident.
  • Decommissioning — delete data, keys, accounts and DNS records properly when a system retires.
The maintenance trap

Software that nobody touches is not “stable” — it is frozen at the security level of its release date. Unused code, forgotten admin panels and abandoned dependencies are where breaches live (the book calls unused code significantly more likely to be insecure).

Chapter 15 · Conclusion & Career

Personal security habits, using AI responsibly, and growing a career in security without burning out.

  • Protect yourself: MFA everywhere, a password manager, passphrases, no password reuse, HaveIBeenPwned alerts, passkeys where offered.
  • You are a target because you are a superuser — be suspicious of “too good to be true”, verify requests for credentials, and ask the security team when unsure.
  • Use AI carefully: review generated code, never give an AI agency over your systems, never paste secrets or private data into it, and check licences and correctness.
  • Use AI as a helper: threat models, documentation, finding vulnerabilities, suggesting fixes, adding comments — all fine, with human review.
  • Grow deliberately: mentors, communities (OWASP, Let’s Talk Software Security), free training, newsletters, and a small number of realistic goals.
  • Appendices — a curated resource list and answer keys for the chapter exercises, so the book can be used as a course.

One-page cheat sheet

SituationDo this
Accepting user inputValidate server-side with an allowlist: type, length, format, range.
Showing data on a pageEncode for the exact context (HTML, attribute, JS, CSS, URL) with the framework’s encoder.
Talking to a databaseParameterized queries / ORM / stored procedures + least-privilege account.
Handling passwordsbcrypt/scrypt/Argon2 + salt, breached-password check, MFA, rate limiting.
Storing keysSecret manager or environment variables; rotate; scan the repo for leaks.
Uploading filesAllowlist types, check headers, rename, store outside the web root, scan for malware.
Calling a shellArgument arrays, shell=False, validated input, least privilege.
Rendering HTML from usersDon’t; if you must, sanitize (DOMPurify / Bleach) and enforce CSP with nonces.
Something failsFail closed, generic error to the user, details to the log.
Adding a dependencyTrusted source, pinned version, CVE check, monitored forever.
ShippingSigned, immutable artifact from a protected CI/CD pipeline.
Running in productionLog, monitor, alert, patch, and test again.
The last word from the book

“Enough” security is risk-based, not perfect. You will not eliminate every vulnerability; you will build layers, make the safe path the easy path, and make sure that when something breaks, it breaks loudly and safely.
