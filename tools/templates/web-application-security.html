Chapter 1 · The History of Software Security

Every modern attack has an ancestor: code-breaking, phone phreaking, early computer hacking — the technology changes, the mindset does not.

  • 1930s — Enigma: the German cipher machine. Security depended on a secret (the rotor settings) and on users believing it was unbreakable.
  • 1940s — Bletchley Park: the bombe automated code-breaking; the lesson is that scale and automation beat individual cleverness.
  • 1950s — Phreaking: manipulating telephone signalling tones (the 2600 Hz whistle, blue boxes) to get free calls. Attacks happen at the layer where trust is assumed.
  • 1960s — Anti-phreaking: phone companies changed signalling — a reminder that fixing the protocol is stronger than banning the tool.
  • 1980s — Computer hacking: BBSes, modems, the first worms and the first computer-crime laws.
  • 2000s — The web: applications moved from static pages to storefronts and user data (see the Apple.com figures), and the browser became the new attack surface.
  • 2015+ — The modern era: professionalised hacking, bug bounties, ransomware, nation-state actors and supply-chain attacks; security became an engineering discipline rather than a hobby.

Chapter 2 · Introduction to Web Application Reconnaissance

Before attacking (or defending) anything, build a map: what exists, where it lives, and which parts nobody is watching.

  • Information gathering — public data first: who owns the domain, what IP ranges, what technologies, what leaked in job listings or GitHub.
  • Passive vs active — passive recon (search engines, archives, certificate logs) is invisible to the target; active recon (port scans, requests) can be detected.
  • Web application mapping — list every host, path, parameter and API version. A real attack surface is a web of apps: marketing site, app, API, admin panel, staging, CDN, third-party services.
Defender’s version of this chapter

You cannot protect assets you do not have in an inventory. Everything recon finds — forgotten subdomains, old API versions, staging servers with debug mode on — is something your defence must also know about.

Chapter 3 · The Structure of a Modern Web Application

The anatomy lesson: REST APIs, JSON, JavaScript’s quirks, SPAs, auth systems, servers, databases, GraphQL, git and CDNs.

  • Modern vs legacy — modern apps are distributed (client, API, services, CDN) and stateful in the browser; legacy apps render everything server-side. Both have trust boundaries, in different places.
  • REST APIs — resources plus HTTP verbs; every endpoint and parameter is attack surface (the book shows Swagger-style docs as a reconnaissance goldmine).
  • JSON — the universal data format of the modern web; parsers, not browsers, must enforce limits on its size and shape.
  • JavaScript essentials that matter for security:
    • Variables and scope — var is function-scoped, let/const are block-scoped; unqualified names become global (and globals can be polluted).
    • Functions and context — this depends on how a function is called, which is why callbacks can leak objects.
    • Prototypal inheritance — objects inherit from prototypes; if an attacker can write to Object.prototype, every object in the app changes.
    • Asynchrony — callbacks and promises mean code runs out of order; race conditions and stale checks become possible.
    • The DOM — the browser’s live object model of the page (Figure 3-3); writing to it with strings is where XSS happens.
  • SPA frameworks — React/Vue/Angular move rendering to the client, so the browser is now the application server: client-side routing, storage and rendering all matter.
  • Authentication vs authorization — proving identity, then deciding permissions; a common bug is doing the first and forgetting the second.
  • Web servers, server-side databases, client-side stores — Apache/Nginx and friends expose versions and default pages; databases hold the crown jewels; localStorage/sessionStorage/IndexedDB are readable by any script on the page, so never store sessions there.
  • GraphQL — one endpoint, client-chosen queries: introspection exposes the whole schema, and queries can be nested into a denial of service.
  • Version control (git) — history is public knowledge; secrets committed once are compromised forever.
  • CDN and cache — they sit between users and origin, and can be abused (cache poisoning, cache deception) or misconfigured (serving stale private data).

Chapter 4 · Finding Subdomains

The homepage is the front door; the interesting bugs live in the side doors — dev., staging., api., old.

  • Multiple applications per domain — one brand owns a “web” of hosts: the app, the marketing site, an API, admin tools, mobile endpoints. Each is a separate application with its own security level.
  • The browser’s built-in network tools — the Network tab shows every request and the domain it went to (Figures 4-2, 4-3). Asynchronous calls reveal internal APIs that are never linked in the UI.
  • Public records, part 1 — search engine caches — operators such as site:mega-bank.com combined with -inurl:www -inurl:mobile surface pages and subdomains that were never advertised (Figure 4-4).
  • Public records, part 2 — accidental archives — Archive.org keeps snapshots going back decades (Figure 4-5). Viewing the source of an old snapshot often reveals subdomains and endpoints that have since been removed from the live app.
  • Public records, part 3 — social snapshots — marketing campaigns, support links and job posts on social platforms leak subdomains; the platforms’ search APIs (Figure 4-6) can be queried for links to the target domain.
  • Zone transfer attacks — a misconfigured DNS server will answer a “zone transfer” request from anyone, handing over its entire list of records — hosts that are not linked from the web app at all.
  • Brute-forcing subdomains — try generated name combinations and see which ones resolve.
  • Dictionary attacks — the efficient version of the same idea: feed a wordlist (dnscan’s top 10,000 subdomains starts with www, mail, ftp, dev, test, admin…) into a script that resolves each candidate. Start with the dictionary, then brute-force what it missed.

Chapter 5 · API Analysis

APIs are where modern applications really live — and they are documented, versioned and often far less protected than the UI in front of them.

  • Endpoint discovery — reuse the same techniques as subdomain hunting: walk the app with the Network tab open, then brute-force and dictionary-attack common paths (/api/, /v1/, /internal/).
  • Authentication mechanisms — work out how each endpoint authenticates: cookies, bearer tokens, API keys, OAuth 2.0 flows. The auth mechanism tells you what an attacker would need to steal.
  • Endpoint shapes — figure out the payload each endpoint expects. Common shapes follow public specs (an OAuth 2.0 authorization endpoint expects response_type, client_id, scope, state, redirect_uri), so the docs tell you the shape.
  • Application-specific shapes — when no spec exists, infer the shape from what the API returns and from the client code that calls it.
  • Versioning and hidden methods — older API versions and unexpected HTTP verbs are usually the least protected part of the surface.
  • Check GraphQL introspection: it can publish the whole schema, including mutations you were never meant to call.

Chapter 6 · Identifying Third-Party Dependencies

Fingerprint what the app is built from: the library and its version is usually the shortest path to a known exploit.

  • Detecting client-side frameworks — SPA frameworks, JavaScript libraries and even CSS libraries leave signatures: global variables, version strings in the console (Figures 6-1, 6-2), asset paths and HTML structure.
  • Detecting server-side frameworks — default error pages, cookie names, header values and URL patterns give the server stack and often its version (the Ruby on Rails example, Figures 6-3, 6-4).
  • HTTP response headers (Server, X-Powered-By) tell you the stack — which is exactly why you should strip them. Obscurity is a weak control, but it is free.
  • Once you know the library and version, CVE databases tell you what is already exploitable — no guesswork required.

Chapter 7 · Identifying Weak Points in Application Architecture

The weakest link is rarely the code you wrote — it is the box you forgot, the cache you trusted, or the environment that reached production.

  • Secure vs insecure architecture signals — compare two apps that do the same thing: the insecure one has no rejection on write, no filtering on read, no encoding on display. Several small findings in the same area usually point at a weak architecture, not one bad method.
  • Multiple layers of security — the same vulnerability can be prevented at several layers. In the book’s messaging example the layers are: API POST → database write → database read → API GET → client read. If only the first layer sanitizes, a new write path silently reopens the hole.
  • Adoption and reinvention — teams often rebuild what already exists (to avoid licences, add features, or because it is fun). Hand-rolled crypto, auth or parsers are a classic architecture-level risk.
  • Edge components — CDN, WAF, load balancers and caches: misconfiguration here affects everything behind them.
  • Storage and environments — public buckets, unprotected backups, staging copies with production data, dev servers with debug mode on, CI systems holding deployment keys.
  • Trust assumptions between services — “internal” traffic that is never authenticated.

Chapter 8 · Part I Summary

Recon turns a single URL into a full map of hosts, APIs, dependencies and weak architecture — and every item on that map is a to-do for your defence.

Remember

Attackers do not start with exploits; they start with inventory. Your defence should begin at the same place: asset inventory, dependency inventory, and an honest list of what is exposed to the internet.

Chapter 9 · Introduction to Hacking Web Applications

The hacker mindset: think in terms of what the developer assumed and then do the opposite — carefully, and legally.

  • Look for missing checks, not broken syntax. Most findings are an assumption (“users will only click this button”) that turns out to be false.
  • Chain small issues: an information leak plus an IDOR plus an XSS can become full account takeover.
  • Recon is not “part before the attack”; it continues during the attack, because every response teaches you something.
  • Ethics and permission come first: scope, authorisation, and responsible reporting.

Chapter 10 · Cross-Site Scripting (XSS)

XSS is what happens when the browser mistakes your data for your program: an attacker’s JavaScript runs with the same powers as yours, inside a victim’s session.

The four flavours

  • Stored XSS — the payload is saved in the database (a comment, profile, filename) and executes for everyone who views it. The most dangerous kind.
  • Reflected XSS — the payload comes back in the same response (a search term printed on the page); the attacker must trick the victim into opening a crafted link.
  • DOM-based XSS — the server never sees the payload; client-side code moves data from a source (URL, storage, postMessage) into a dangerous sink (innerHTML, eval).
  • Mutation-based XSS — the browser’s own parser “fixes” malformed HTML in a way the sanitizer did not predict, resurrecting a script.

Discovery comes from putting test strings into every input and watching whether they come back unescaped. Filter bypassing comes from encoding tricks, unusual tags, event handlers and context switches — which is why the book keeps insisting that filtering is not the defence; encoding and CSP are.

XSS: the one-line difference that mattersvulnerable → safe
// 1. Any script gets to execute — user data became code
document.getElementById("out").innerHTML = userInput;

// 2. Text stays text
document.getElementById("out").textContent = userInput;

// 3. If HTML really is required, sanitize first
document.getElementById("out").innerHTML = DOMPurify.sanitize(userInput);

Chapter 11 · Cross-Site Request Forgery (CSRF)

CSRF does not steal the session — it borrows it. The victim’s browser is tricked into sending a request the user never intended.

  • Query parameter tampering — a state-changing GET (/transfer?to=evil&amount=100) can be triggered by a link or an <img>.
  • Alternate GET payloads — images, iframes, script tags: anything the browser fetches automatically (Figure 11-2).
  • CSRF against POST endpoints — a hidden auto-submitting form sends a “legitimate” POST with the user’s cookies (Figure 11-3).
  • Bypassing weak defences — checking the Referer is often bypassable with data:/javascript: URLs or when the header is stripped; a token that is not validated, is reused, or is not tied to the session is no defence.
  • The core condition: the action is predictable, cookie-authenticated, and there is no unforgeable per-request secret.

Chapter 12 · XML External Entity (XXE)

XML lets a document define its own “entities”. If the parser resolves external ones, your file becomes a way to read files from — and send data out of — the server.

  • Direct XXE — the attacker’s request contains a DTD that loads a local file (e.g. /etc/passwd) and the response leaks it.
  • Indirect XXE — the malicious DTD lives on the attacker’s server, so the payload is tiny and harder to detect.
  • Out-of-band exfiltration — when nothing is reflected, data is pushed out via a parameterised entity pointing at an attacker-controlled host.
  • Escalation — XXE is not just file read: it can reach internal services (SSRF), and the book walks an account-takeover workflow built from it.
XXE: three lines that make it impossible (Java shown; every parser has an equivalent)safe
DocumentBuilderFactory f = DocumentBuilderFactory.newInstance();
f.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
f.setFeature("http://xml.org/sax/features/external-general-entities", false);
f.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
f.setXIncludeAware(false);
f.setExpandEntityReferences(false);

// better still: if the API can accept JSON, do not accept XML at all.

Chapter 13 · Injection

Injection is one idea in many costumes: user data enters an interpreter and is interpreted as instruction — SQL, code, or shell commands.

  • SQL injection — the classic: string concatenation turns a login form into “return every row”. The book demonstrates old-school PHP/MySQL and how to build payloads for APIs.
  • Code injection — user input reaching eval, Function, templates, or a deserializer: data becomes program.
  • Command injection — input concatenated into a shell command; a semicolon is enough.
  • Exfiltration techniques — union queries, error-based leaks, blind/boolean inference, time-based delays, out-of-band channels.
  • Bypassing defences — encoding, comments, alternative syntax and case tricks defeat naive blocklists; only parameterisation and argument arrays reliably stop injection.
SQL injection (string-built query)vulnerable
const q = "SELECT id FROM users " +
          "WHERE email='" + email +
          "' AND pass='" + pass + "'";
// email = "' OR '1'='1"  →  every user matches
Parameterized querysafe
const q = "SELECT id FROM users " +
          "WHERE email=? AND pass=?";
db.query(q, [email, pass]);   // values are
                              // never parsed as SQL

Chapter 14 · Denial of Service

Availability is part of security: if the attacker can make the app unusable, that is a successful attack — no data theft required.

  • Regex DoS (ReDoS) — a cleverly crafted string makes a badly written regular expression take exponential time; one request can pin a CPU core.
  • Logical DoS — abusing normal features: giant file uploads, deeply nested JSON or GraphQL, huge page sizes, expensive searches, unbounded loops.
  • DDoS — many machines; the attacker’s traffic looks like a crowd, so per-IP rate limiting is not enough.
  • Advanced DoS — slowloris-style slow requests, connection exhaustion, amplification attacks.

Chapter 15 · Attacking Data and Objects

Three attacks that go after your model of the data rather than your syntax: mass assignment, IDOR and unsafe serialization.

  • Mass assignment — the API blindly copies every JSON field into a database object, so the attacker adds "isAdmin": true or "balance": 999999.
  • Insecure Direct Object Reference (IDOR) — the endpoint trusts the identifier in the request (/invoice?id=1001 → try 1002) without checking that this user owns that object.
  • Serialization attacks — the server turns attacker-supplied bytes into live objects, letting the attacker choose which class gets instantiated (and often execute code).
Mass assignment and IDOR, side by sidevulnerable
// mass assignment: every field the client sends is trusted
Object.assign(user, req.body);           // includes { "isAdmin": true }

// IDOR: the object id is trusted, ownership never checked
app.get("/invoice", (req, res) =>
  db.invoices.findById(req.query.id).then(res.json));
  // ?id=1002 returns someone else's invoice
The same two endpoints, fixedsafe
// allowlist the fields a client may set
const { name, email } = req.body;
db.users.update(req.user.id, { name, email });

// authorize the object, not just the route
const inv = await db.invoices.findById(req.query.id);
if (inv.ownerId !== req.user.id) return res.status(403).end();

Chapter 16 · Client-Side Attacks

Attacks that live entirely in the browser: poison the prototype, frame the page, or swap the tab underneath the user.

  • Prototype pollution — a recursive merge or a JSON parse writes __proto__, so every object in the app suddenly has attacker-chosen properties (often escalating to XSS or auth bypass).
  • Clickjacking — your site is loaded in a transparent iframe over a decoy page, so clicks meant for the decoy hit your real buttons.
  • Tabnabbing / reverse tabnabbing — a link with target="_blank" without rel="noopener" gives the new page a handle on your tab, which it can silently replace with a phishing page.
Prototype pollution: how one merge ruins everythingvulnerable
function merge(target, source) {
  for (const k in source) {
    if (typeof source[k] === "object") merge(target[k], source[k]);
    else target[k] = source[k];
  }
}
merge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'));

({}).isAdmin;   // true — for every object in the process

Chapter 17 · Exploiting Third-Party Dependencies

You did not write most of your application — and most of the code that reaches production comes from somewhere else.

  • Methods of integration — direct dependency, transitive dependency, CDN-hosted script, embedded widget, container image.
  • Package managers — npm, Maven, PyPI and friends: typosquatting, malicious packages, dependency confusion, compromised maintainer accounts.
  • CVE / NVD databases — the public catalogue of known vulnerabilities scored by severity; matching your versions against it is step one.

Chapter 18 · Business Logic Vulnerabilities

No scanner will find these: the code works exactly as written, but the rules can be bent. This is where real money is lost.

  • Custom maths — negative quantities, rounding errors, percentages applied twice, “free item” thresholds reached with refunds.
  • Programmed side effects — each step is fine, but the order or repetition of steps produces an unintended outcome (apply coupon, cancel order, re-apply coupon).
  • Quasi-cash attacks — abusing refunds, gift cards and credits so that value can be converted into money.
  • Vulnerable standards and conventions — assuming a payment, email or shipping partner enforces something they do not.
  • Exploiting them — replaying a whole workflow, skipping steps, or running two workflows in parallel so each check sees a consistent world (a race condition at business level).
Why these matter most

A framework and a WAF fix the “known” categories. Business logic has no library to import — it needs threat modeling, misuse cases and monitoring of real behaviour (Chapter 36).

Chapter 19 · Part II Summary

Ten attack families, one pattern: the application trusted something it should have verified — data, an identifier, a field, a token, a dependency, or a business rule.

Chapter 20 · Securing Modern Web Applications

Defence is a programme, not a patch: architecture, code review, discovery, analysis, management, regression testing and mitigation.

  • Defensive architecture — design so that a single mistake cannot become a breach (segmentation, least privilege, isolation).
  • Comprehensive code reviews — human review plus automation, focused on what changed and on the risky parts.
  • Vulnerability discovery → analysis → management — find them, understand them, rank them, fix them, verify the fix.
  • Regression testing — a fixed bug must stay fixed; add a test for every vulnerability you close.
  • Mitigation strategies — remove the feature, fix the root cause, add a compensating control, or accept the risk with eyes open (in that preference order).
  • Use your recon and offence knowledge — the same map and the same techniques, applied by you before someone else applies them.

Chapter 21 · Secure Application Architecture

Security decisions that are cheapest at design time: how users authenticate, what data is sensitive, what third parties see, and how much you trust the network.

  • Analyse feature requirements for security impact — every feature is a new way in; ask what it lets an attacker do.
  • Authentication and authorization — TLS everywhere, strong password storage, MFA (Figure 21-2), least privilege, and authorization checks that follow the data, not just the route.
  • PII and financial data — minimise collection, encrypt, tokenize, and never let it spread into logs, analytics or test environments.
  • Search engines and data stores — an Elasticsearch instance with no auth is a classic breach (Figure 21-3); anything with a query interface is an asset to protect.
  • Zero Trust — every request is authenticated and authorized, even from inside the network; identity is the new perimeter.

Chapter 22 · Secure Application Configuration

The browser is controlled by headers, cookies and policies — this chapter is the checklist that makes the browser fight on your side.

  • Content Security Policy — declare the allowed sources for scripts, styles, images and frames; prefer nonces or hashes over unsafe-inline; add object-src 'none' and base-uri 'none'.
  • CORS — be explicit. Access-Control-Allow-Origin: * together with credentials, or reflecting any Origin, hands your API to every website.
  • Headers — HSTS, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy; remove version banners.
  • Cookies — Secure, HttpOnly, SameSite, tight Path and Domain, short lifetime.
  • Framing and sandboxing — frame-ancestors / X-Frame-Options against clickjacking, and the sandbox attribute for untrusted content.
CORS: the difference between a policy and an open doorvulnerable
// reflects any origin AND allows credentials
res.setHeader("Access-Control-Allow-Origin", req.headers.origin);
res.setHeader("Access-Control-Allow-Credentials", "true");
An allowlist insteadsafe
const allowed = new Set(["https://app.example.com"]);
if (allowed.has(req.headers.origin)) {
  res.setHeader("Access-Control-Allow-Origin", req.headers.origin);
  res.setHeader("Access-Control-Allow-Credentials", "true");
  res.setHeader("Vary", "Origin");
}

Chapter 23 · Secure User Experience

Your error messages, timing and screens are an information channel: they tell an attacker which accounts exist, which features are enabled, and what the system is built from.

  • Information disclosure and enumeration — “user not found” versus “wrong password”, different response times, different status codes, and registration forms that reveal existing accounts.
  • Generic responses — one message for all authentication failures, with the real reason only in the logs.
  • UX best practices — clear, consistent security flows (login, reset, MFA) that do not tempt users into workarounds; consistent naming so users can recognise genuine pages (Figure 23-1 uses React’s naming patterns as the example).
  • Don’t design leaks in — verbose errors, debug pages, exposed API docs and “helpful” autocomplete can all be turned against you.

Chapter 24 · Threat Modeling Applications

A structured conversation about how your specific application could be attacked — done before the code exists, and repeated when it changes.

  • Design an effective model — scope, assets, actors, entry points, trust boundaries, and a list of threats with owners.
  • By example — the book walks a real application end to end, asking at each step: what data is this, who can reach it, what happens if it is wrong or malicious?
  • Output must be actionable — each threat gets a mitigation, an owner and a deadline; otherwise it is just a document nobody reads.
  • Re-run it on every architectural change, new integration and new feature.

Chapter 25 · Reviewing Code for Security

You cannot read everything, so read the right things: entry points, trust boundaries, auth code, and the places where data becomes code.

  • Where to start — new/changed code, public endpoints, authentication and authorization, file handling, database access, and anything that handles money or secrets.
  • Archetypical vulnerabilities vs business logic — pattern-based bugs (injection, XSS) are findable with tools and checklists; logic bugs need the product’s rules in your head.
  • Anti-patterns to grep for — eval, innerHTML, string-built SQL, shell=True, pickle, verify=False, Access-Control-Allow-Origin: *, hard-coded secrets, commented-out auth checks.
  • Review the diff, not just the file — and require a second reviewer for security-sensitive changes (git hosts make this natural, Figure 25-1).

Chapter 26 · Vulnerability Discovery

Finding your own bugs is cheaper than reading about them in a breach report: automate the boring parts, then add humans.

  • Security automation — SAST (source), DAST (running app), IAST (instrumented), SCA (dependencies), secret scanning and fuzzing; the book uses Jest (Figure 26-1) as an example of testing integrated into the workflow.
  • Responsible disclosure — give researchers a way to report; a security.txt and a stated policy are cheaper than a public Twitter thread.
  • Bug bounty programmes — HackerOne-style platforms (Figure 26-2) bring many eyes, but need triage capacity and a reputation for paying.
  • Third-party penetration testing — an independent, time-boxed attack by experts; best value after the basics are done.

Chapter 27 · Vulnerability Management

A vulnerability you cannot rank, reproduce and assign is a vulnerability you will not fix.

  • Reproduce — a finding you cannot reproduce is a rumour. Capture exact steps, request, response and impact.
  • Rank with CVSS — base score (intrinsic severity: attack vector, complexity, privileges, user interaction, and impact on C/I/A), temporal score (exploit maturity, remediation level, confidence), environmental score (how much it matters to your system).
  • Beyond scoring — add business context (is this the payment service or a brochure page?), asset criticality, and existing compensating controls.
  • Then manage — assign an owner, set a deadline by severity, track to closure, and re-test the fix.
The two extra dimensions

Temporal (Figure 27-3) asks: is there a working exploit yet, and is there a fix? Environmental (Figure 27-4) asks: how much does this specific system matter to us? Two identical CVEs can deserve very different urgency in two different companies.

Chapter 28 · Defending Against XSS Attacks

Stop treating user data as HTML. Encode on output, sanitize when HTML is genuinely required, and let CSP catch what you missed.

  • Coding best practices — encode for the exact context (HTML body, attribute, JavaScript, CSS, URL), prefer framework auto-escaping, avoid innerHTML/eval, and never build DOM from strings.
  • Sanitizing input — use a maintained parser-based sanitizer (DOMPurify) with a strict allowlist of tags and attributes; never a regex.
  • CSS XSS and mutation XSS — old browsers and clever markup can revive scripts; keep sanitizers updated and keep CSP as the backstop.
  • CSP for XSS prevention — nonce- or hash-based script-src, no unsafe-inline, object-src 'none', and Trusted Types in browsers that support them.
Encode for the context you are actually insafe
// HTML body      →  <  becomes &lt;
el.textContent = data;

// HTML attribute →  quotes must be encoded too
el.setAttribute("title", data);      // not  '<div title="' + data + '">'

// URL component  →  percent-encode
location.href = "/search?q=" + encodeURIComponent(q);

// JavaScript     →  JSON-encode, never string-concatenate
<script>const cfg = JSON.parse('<%= jsonEncode(config) %>');</script>

Chapter 29 · Defending Against CSRF Attacks

Make each state-changing request carry something an attacker’s page cannot know or guess.

  • Header verification — check Origin, Referer and the Sec-Fetch-Site metadata headers; reject cross-site state changes.
  • CSRF tokens — a random, per-session (or per-request) token, validated server-side on every state-changing request, sent in a header or a hidden field.
  • SameSite cookies — Lax or Strict blocks most cross-site sending; combine with tokens for defence in depth.
  • Design rules — never use GET for state changes, require re-authentication for sensitive actions, and use POST/PUT/DELETE with tokens.
Middle-of-the-stack CSRF checksafe

Chapter 30 · Defending Against XXE

Turn off the dangerous XML features — external entities and DTDs — or don’t accept XML at all.

  • Disable DTD processing, external general entities and external parameter entities; disable XInclude and entity expansion (which also stops entity-expansion denial-of-service attacks).
  • Use a hardened, up-to-date parser and set secure defaults in one shared utility so nobody has to remember.
  • Evaluate other formats — JSON, YAML, CSV and even SVG have their own parser risks (YAML tags, SVG scripts); the point is that “we switched to JSON” must be checked, not assumed.
  • Advanced XXE risks — SSRF, internal port scanning and denial of service through entity expansion.

Chapter 31 · Defending Against Injection

Keep code and data in separate lanes, and give the interpreter as little authority as possible.

  • SQL injection — parameterized queries, prepared statements, stored procedures, least-privilege database accounts, and no dynamic SQL built from strings.
  • Generic injection defences — validate with allowlists, escape for the right context when parameterisation is impossible, avoid shells entirely, and never pass user input to eval, exec, system, Function or a template compiler.
  • Principle of least authority (Figure 31-1) — if the query engine, the OS user and the container can only do the minimum, a successful injection is far less useful.
  • Detect as well as prevent — log and alert on query errors and on input that looks like injection; attacks often need many attempts.

Chapter 32 · Defending Against DoS

Put limits on everything an attacker can inflate: time, size, depth, connections and cost.

  • Regex DoS — avoid nested quantifiers and catastrophic backtracking; bound input length before matching; use RE2-style engines or timeouts.
  • Logical DoS — cap upload size, page size, nesting depth, query complexity (especially GraphQL) and expensive searches; add per-user quotas and caching.
  • DDoS — rate limiting at the edge, CDN absorption, scrubbing services, autoscaling, and blackholing as a last resort (Figure 32-1).
  • Operational — timeouts on every outbound call, circuit breakers, and monitoring that alerts on abnormal resource use.

Chapter 33 · Defending Data and Objects

Decide which fields a client may write, verify who owns every object, and stop creating objects out of untrusted bytes.

  • Mass assignment — explicit allowlists of assignable fields (DTOs or dedicated input schemas), never a blind copy of the request body; separate “user-editable” from “server-controlled”.
  • IDOR — authorize every object access against the current user (ownership or role), use unguessable identifiers as a second layer, and log access to sensitive records.
  • Serialization attacks — do not deserialize untrusted data into objects; prefer plain JSON with schema validation; if you must, use allowlists, signing and integrity checks.

Chapter 34 · Defense Against Client-Side Attacks

Harden the browser environment: clean objects, no framing, safe links, and isolation between origins.

  • Prototype pollution — Object.create(null) for dictionaries, Object.freeze(Object.prototype) where practical, reject __proto__/constructor/prototype keys, and use maintained merge libraries.
  • Clickjacking — Content-Security-Policy: frame-ancestors 'none' (or X-Frame-Options: DENY) plus frame-busting for legacy clients.
  • Tabnabbing — rel="noopener noreferrer" on every target="_blank" link.
  • Isolation policies — COOP, COEP and CORP put your origin in its own process and refuse cross-origin embedding, which also blocks a range of side-channel and XS-Leak attacks.

Chapter 35 · Securing Third-Party Dependencies

Treat every dependency as code written by a stranger that will run with your privileges — because that is exactly what it is.

  • Evaluate dependency trees (Figure 35-1) — one direct dependency can pull in hundreds of transitive ones; know how deep the tree goes and how many maintainers stand behind it.
  • Secure integration — lockfiles and pinned versions, verified registries, subresource integrity for CDN scripts, vendoring critical libraries, and reviewing updates rather than auto-merging them.
  • Continuous monitoring — SCA on every build, alerts for new CVEs, a policy for how fast to patch, and a plan for when a package is abandoned.
  • Least privilege for dependencies — a library does not need your database credentials, your network access, or your production secrets.

Chapter 36 · Mitigating Business Logic Vulnerabilities

Since no signature can catch a wrong rule, you defend with architecture, invariants and statistics.

  • Architecture-level mitigations — one place that calculates money, immutable transaction records, server-side prices, explicit state machines and idempotency keys so a step cannot be replayed.
  • Validate the whole flow — check that the steps happened in order and only once; never trust a client-supplied state.
  • Statistical modelling — fraud detection on behaviour: velocity of orders, refund patterns, impossible geography, amounts that sit just under a limit.
  • Human review and alerts — the anomaly that no rule predicted is exactly what monitoring is for.
  • Test the rules, not just the code — write misuse cases (“apply the coupon twice”, “cancel after refund”) as automated tests.

Chapter 37 · Part III Summary & Conclusion

The whole book in one loop: map the surface, think like an attacker, design and configure for defence, then review, test, score and fix — forever.

  • History — the attacks change shape, the assumptions behind them do not.
  • Recon — inventory is security. You cannot protect what you have not found.
  • Offense — every attack class exploits an unverified assumption: data as code, request as intent, id as authority, library as trusted, rule as enforced.
  • Defense — architecture and configuration prevent, encoding and parameterisation neutralise, CSP and headers contain, monitoring and management recover.
  • Keep learning — the book closes with what to study next: protocols, cryptography, cloud, and the human side of security.
