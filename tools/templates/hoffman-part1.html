Part I in one page

Recon is building a map of an application — technical and functional — so you know what to attack and in which order. Recon skills on their own are worth little; they become valuable when combined with offensive knowledge (what to do with the map) and defensive experience (what the defenders probably did).

The book opens Part I with a philosophical point that is easy to skip and important not to: a hacker must understand the application as a business, not just as code. Who are its users? How does it earn money? Why do users pick it over competitors? Without that, you cannot tell which data and which features actually matter. A car-sales site treats inventory and prices as mission-critical; a hobby site where enthusiasts post photos of their own cars treats user accounts as the crown jewels.

The four things Part I teaches you to map

  • The business and the roles (Chapter 2) — what the app does, who uses it, and what privileged interfaces must exist behind it (admin, teller, moderator).
  • The hosts (Chapter 4) — every subdomain and server attached to the domain. The main site is the most hardened part; the interesting things live on the side doors.
  • The API surface (Chapter 5) — endpoints, HTTP verbs, authentication scheme, and the payload shape each endpoint expects.
  • The stack and its weak points (Chapters 3, 6, 7) — frameworks, servers, databases, libraries and versions; then the architectural signals that say “many bugs live here”.
Read this before you try anything

The book is explicit: these techniques can get your IP flagged, your account banned, or land you in legal trouble. Only perform them against applications you own or have written permission to test. Several techniques in this Part (verb fuzzing, brute forcing) can delete or modify real data.

Why a defender should read Part I

Every technique here is a question your own application must be able to answer: do I know all my subdomains? Do I know which headers leak my stack? Do I know where my authorization checks live? Recon is also the cheapest form of self-audit — you find the weak mechanism before someone else does.

Chapter 2 · Introduction to Web Application Reconnaissance

The user interface is not the application. What you can click is a small, curated subset of what actually exists — and the rest is what recon is for.

What recon actually is

  • Definition — the explorative data-gathering phase that happens before attacking. Hackers, pen testers and bug-bounty hunters do it; security engineers should do it too, to find weakly secured mechanisms and fix them first.
  • Recon alone is not valuable — the skill becomes valuable when paired with offensive knowledge (how to use the map) and defensive experience (what the defenders probably forgot).
  • You are not “inside” the UI — even public apps expose only part of their interface. Assume you are seeing a subset until proven otherwise.
  • You do not need a UI at all — you can map an application you have no access to, purely by reverse-engineering the structure of its APIs and the payloads they accept.

The MegaBank thought experiment: why hidden interfaces must exist

The book walks through a normal bank account: you open a checking account in a branch, a teller types it in, later you can view your balance online, and a banker can add a savings account or close your account for you. You — the customer — can read, but you cannot create, modify or delete your own account online. So somebody else must have an application that can. That reasoning produces this table (the book’s own):

User typePositionPermissions
CustomerExternalLog in to the website. Read account balance via the web UI.
TellerInternalCreate new accounts when provided paperwork from a customer.
BankerInternalModify existing accounts on behalf of customers.

Conclusions the book draws from this:

  • Large organisations cannot have developers hand-writing database queries per operation, so there is automation behind the scenes that external users never see.
  • That automation almost always uses tiered permissions — role-based access control (RBAC). Very few applications give every user one single permission level.
  • Walking the UI will never show you the endpoints meant for moderators or admins — but recon often can. You can even map the full permission set of an admin and compare it with a normal user’s.
  • Occasionally you find a glitch that lets a non-privileged user reach privileged functionality. That glitch is the vulnerability.
  • Sometimes you meet servers or APIs that are protected by nothing at all — one forgotten firewall rule puts an internal server on the public internet.

Web application mapping: write it down

The book uses “map” the way geography does: the features, shapes and surfaces of an application. A map can be scratch notes for a small target, or a structured document for a big one. The only real requirements are that it stays traversable and that it preserves relationships and hierarchies. Hoffman prefers JSON-like notes and suggests tools such as Notion or XMind.

The pattern to notice

Chapter 3 · The Structure of a Modern Web Application

You cannot recognise a misconfiguration if you do not recognise the component. This is the anatomy lesson: REST, JSON, JavaScript, the DOM, SPAs, auth systems, servers, databases, GraphQL, git and CDNs.

Modern vs legacy applications

  • Ten years ago — server-side frameworks rendered an HTML page and sent it to the browser; to update anything, the client requested another whole page. Then AJAX arrived and pages learned to make requests from inside a session.
  • Today — the “application” is usually several applications talking over a network: a client app plus one or more stateless REST APIs, plus storage and third-party services.
  • The browser app is a real application — it boots once, manages its own lifecycle, requests its own data, and no longer reloads pages. One client commonly talks to several different servers (e.g. one host for images, another for logins and data).

The book’s list of what a typical modern app is built from: REST API · JSON or XML · JavaScript · an SPA framework (React, Vue, Ember, Angular) · an authentication and authorisation system · one or more web servers (usually Linux) · web server software (Express, Apache, NGINX) · one or more databases (MySQL, MongoDB…) · a client-side data store (cookies, web storage, IndexedDB).

REST APIs in plain language

REST (Representational State Transfer) is a set of rules for an API. The book’s four defining traits:

  1. Separate from the client — the client can request resources but cannot run server logic or touch the database directly.
  2. Stateless — the API stores nothing about the caller’s connection. It can still authenticate and authorise, but the proof travels on every request (usually a token).
  3. Cacheable — responses can be marked cacheable or not, which is how these APIs scale. Badly managed caches leak one user’s data to another.
  4. One endpoint per object or method, organised hierarchically — e.g. /moderators/joe/logs/12_21_2018. Combined with HTTP verbs, the API becomes self-documenting: DELETE /moderators/joe/logs/12_21_2018 does exactly what it reads like.
HTTP verbREST meaningEveryday translation
POSTCreateMake a new thing
GETReadShow me the thing
PUTUpdate / replaceReplace the thing with this
PATCHUpdate / modifyChange part of the thing
DELETEDeleteRemove the thing

REST vs SOAP: older enterprise apps used SOAP, which always speaks XML. REST targets data rather than functions, caches easily and scales better; it accepts any data format, and in practice that format is JSON. That is why SOAP/XML is now mostly found in legacy enterprise systems.

JavaScript — the parts that matter for security

Servers can run any language; the browser only runs JavaScript. That is why every example in this book — and in Part I especially — is JavaScript. Five quirks are worth knowing before any of it makes sense:

1. Variables and scope

Four ways to declare the same variable — four different behavioursbook code
// global definition — no keyword at all
age = 25;

// function scoped
var age = 25;

// block scoped
let age = 25;

// block scoped, without reassignment
const age = 25;
  • No keyword → global. The variable is hoisted to global scope and also appears as a property of window, where any other script can read or overwrite it. That is a name-collision risk and a real security risk.
  • var → function-scoped. Declared inside an if block but inside a function, it is still visible after the block — the classic source of confusing bugs.
  • let → block-scoped. Same code, but now the variable is gone once the block ends. Fewer scope bugs.
  • const → block-scoped and cannot be reassigned (like final in Java).
The global leak, demonstratedrisky
// define global integer
age = 25;

console.log(age);        // 25 — direct call
console.log(window.age); // 25 — same thing, via the window object

2. Functions and context

Functions in JavaScript are objects: they can be assigned, passed and redefined. They come as anonymous functions, named functions, arrow (shorthand) functions that share their parent’s context, and the IIFE — an immediately invoked function expression, (function(){})(), used to run code in its own scope. Every function carries a this context that can be moved around with bind, call and apply.

Moving context between functionsbook code
// create a new getAge() clone bound to the ageData context
const getBoundAge = getAge.bind(ageData)('joe');

// invoke immediately with a supplied context
const boundAge = getAge.call(ageData, 'joe');
const boundAge2 = getAge.apply(ageData, ['joe']);

// arrow functions inherit context instead of defining their own
const soup = { garlic: true };
soup.hasGarlic1 = function() { console.log(this.garlic); }; // true
soup.hasGarlic2 = () => { console.log(this.garlic); };       // false

3. Prototypal inheritance

There are no classes underneath — objects inherit from other objects through a prototype chain. Every object has a prototype pointer back to the function that created it. That single mechanic is why prototype pollution (Part II) is possible: write to Object.prototype and every object in the application inherits your value.

4. Asynchrony

Network requests take unpredictable time. Instead of waiting, JavaScript fires requests and describes what to do when they finish. Three generations of doing this:

Three ways to chain the same three requestsbook code
// 1. Callbacks — fast, but a pyramid of doom
getUser(function(user) {
  getUserProfile(user, function(profile) {
    setUserProfileConfig(profile, config, function(result) {
      console.log('success!');
    });
  });
});

// 2. Promises — vertical, with one place for errors
new Promise((resolve, reject) => { /* ... */ })
  .then((user) => { /* ... */ })
  .then((profile) => { /* ... */ })
  .catch((err) => console.log('an error occurred!'));

// 3. async / await — reads like synchronous code
const setUserProfile = async function() {
  let user        = await getUser();
  let userProfile = await getUserProfile(user);
  let setProfile  = await setUserProfile(userProfile, config);
};
setUserProfile();
Why this matters for recon scripts

Because requests can run concurrently, a recon script fires hundreds of DNS lookups or HTTP requests at once instead of waiting for each one. That is the difference between a brute force that takes minutes and one that takes days (Chapter 4 depends on it).

5. The browser DOM

The DOM is the browser’s standard library and its hierarchical model of the page. Its two main objects are window and document, defined by a spec maintained by WHATWG. Functions such as document.querySelector() look like JavaScript but are DOM methods. For security, the DOM is where data becomes markup — i.e. where XSS appears.

SPA frameworks

Old sites were ad-hoc scripts plus reused HTML templates — fine for static pages, useless for app-like behaviour. Single-page application frameworks closed that gap: they hold their own state, are built from reusable components with their own lifecycles, and deliver near-desktop experiences (Facebook, YouTube). The big open-source ones are React, Ember, Vue and Angular. They all sit on top of JavaScript and the DOM, and they add complexity from a security point of view — client-side routing, client-side storage and client-side rendering all become attack surface.

Authentication and authorisation

Authentication (AuthN)Authorisation (AuthZ)
Question“Are you really joe123?”“What may joe123 touch?”

  • HTTP Basic — Authorization: Basic <base64(user:password)> on every request. Supported by every browser, but the session never expires and the credentials are trivially decoded (atob()). Base64 is encoding, not encryption.
  • Digest — hashes instead of base64, so harder to intercept and replay; the strength depends entirely on the hash used.
  • OAuth — a big provider vouches for your identity with a token. Convenient (one place to update your data), but one compromised provider account compromises every connected app.
  • MFA — usually layered on top, so a stolen password is not enough.
The architectural tell the book gives you

Well-designed applications centralise authorisation in one class. Poorly written APIs re-implement the check in every endpoint — and by human error, some of those copies will be missing. If you spot per-endpoint hand-rolled checks, expect to find the one that forgot.

Servers, databases and client-side storage

  • Web servers — application logic sits on web server software, which sits on Linux, which sits on hardware. Apache (~half of all sites, since 1995), NGINX (~30%, growing, far less overhead per connection) and Microsoft IIS (Microsoft-specific stacks). Knowing the big three is how you later spot configuration-based vulnerabilities rather than logic bugs.
  • SQL databases — still the default: PostgreSQL, SQL Server, MySQL, SQLite. Strict but fast and easy to query.
  • NoSQL — MongoDB, DocumentDB, CouchDB: flexible “documents”, weaker at querying and aggregating.
  • Specialised stores — e.g. Elasticsearch for search, synchronised with the main database.
  • Multiple databases at once is normal — and dangerous: an app with perfect SQL handling may have wide-open MongoDB or Elasticsearch queries and permissions.
  • Client-side stores — localStorage (persistent key/value, protected by the browser’s same-origin policy), sessionStorage (gone when the tab closes), and IndexedDB (an in-browser queryable NoSQL database).
The book’s warning about client stores

In poorly architected applications, client-side data stores can reveal sensitive data such as authentication tokens or other secrets. If a token lives in localStorage, any XSS on the site can read it.

GraphQL

GraphQL wraps existing endpoints and lets the client ask for exactly the fields it wants, bundling several requests into one network hop. That is great for performance and offers richer features (aliases, fragments, variables, directives, mutations). The recon twist: the client is now writing the query, so the server must bound what a query is allowed to cost.

Version control, CI/CD and CDNs

  • Git — branches, stashes and history, and hosts like GitHub and GitLab on top. History is recon material: it shows how the code evolved, what was removed, and what was accidentally published.
  • CI/CD — pushes trigger tests and deployments. The book’s key sentence: security is no longer tied only to the network stack and application code, but also to the version-control system and the delivery pipeline. A compromise at either layer can be catastrophic.
A normal Git workflow (and where secrets like to hide)book code
git init
git remote add origin <github-repository-url>
touch .gitignore
echo "node_modules" > .gitignore
git add -A
git commit -m "initial commit"
git push --set-upstream origin main

The .gitignore is the interesting line: whatever is not listed there gets committed forever. A key removed in a later commit still lives in history.

Chapter 4 · Finding Subdomains

The consumer-facing site is the most-watched, most-patched part of any company. The interesting bugs live on the subdomains nobody brags about.

The mindset first

Walking a public app and watching its network traffic only gets you so far. What you actually want is the list of hosts attached to the domain that are not linked from the public app at all — admin panels, APIs, dev and staging environments, mail and internal tools.

Technique 1 — the browser’s own network tools

Open DevTools → Network and watch every request: the request URL tells you which domain something was sent to or served from. Asynchronous calls are the valuable ones, because they often point at hosts the UI never links to.

Technique 2 — public records: search engine caches

Google has more indexed data than anyone, but a raw search is too noisy. The trick is operators: site: restricts the domain, -inurl: removes the parts you already know about.

Filtering a site down to the parts you have not seenbook code
site:mega-bank.com log in

site:mega-bank.com -inurl:www -inurl:mobile

The first query finds login pages across the domain. The second removes the main site and the mobile site, so what remains is the interesting long tail. Repeat until no new results appear, and try other engines — they support the same operators.

Technique 3 — public records: accidental archives

Archive.org keeps snapshots of websites going back decades (the New York Times alone has over 500,000 home-page snapshots since 1996). Old snapshots contain links and code that were removed from the live app but were once public — old subdomains, old download paths, old parameters.

The book’s manual recipe: open ten archives from ten dates spaced far apart → “View source” → select all → copy into a single legacy-source.html → search that file for http://, https:// and file:// to pull out every host that ever appeared.

Technique 4 — public records: social snapshots

Marketing campaigns, support links and recruiting posts leak subdomains. Every major platform offers a data/search API that can be queried for links to the target domain. The book’s example is the X (Twitter) search API:

Querying a social search API for links to the target domainbook code
curl --request POST \
  --url https://api.twitter.com/1.1/tweets/search/30day/Prod.json \
  --header 'authorization: Bearer <MY_TOKEN>' \
  --header 'content-type: application/json' \
  --data '{
           "maxResults": "100",
           "keyword": "mega-bank.com"
           }'

Then scan the returned text for links: they tend to reveal hosts tied to campaigns, trackers and hiring events. Note the ethical caveat the book raises — this analyses data about ordinary users, so use it only within an authorised engagement.

Technique 5 — DNS zone transfer attacks

DNS turns names into IP addresses, and DNS servers keep their records in a zone file. Zone transfers exist so that a secondary server can copy the zone from the primary. If the primary does not restrict who may ask, anyone can ask — and receive the entire record list, including hosts that are not linked from the web app.

Ask for the nameservers, then ask one of them for the zonebook code
# 1. who serves DNS for the domain?

# 2. pretend to be a secondary server and request the zone file
host -l mega-bank.com ns1.bankhost.com

Technique 6 — brute forcing subdomains

Last resort, and noisy: attempts are easily logged and rate-limited, and network latency (50–250 ms per request) makes naive loops unbearably slow. So the script is asynchronous — fire everything, then collect.

Generate every candidate name up to a lengthbook code
const generateSubdomains = function(length) {
  const charset = 'abcdefghijklmnopqrstuvwxyz'.split('');
  let subdomains = charset;
  let subdomain, letter, temp;

  for (let i = 1; i < length; i++) {
    temp = [];
    for (let k = 0; k < subdomains.length; k++) {
      subdomain = subdomains[k];
      for (let m = 0; m < charset.length; m++) {
        letter = charset[m];
        temp.push(subdomain + letter);
      }
    }
    subdomains = temp;
  }
  return subdomains;
};

const subdomains = generateSubdomains(4);
Resolve every candidate concurrently with Node’s DNS librarybook code
const dns = require('dns');
const promises = [];

subdomains.forEach((subdomain) => {
  promises.push(new Promise((resolve, reject) => {
    dns.resolve(`${subdomain}.mega-bank.com`, function (err, ip) {
      return resolve({ subdomain: subdomain, ip: ip });
    });
  }));
});

Promise.all(promises).then(function(results) {
  results.forEach((result) => {
    if (!!result.ip) { console.log(result); }
  });
});

Two engineering details the book highlights: dns.resolve is used instead of dns.lookup because lookup only looks asynchronous — underneath it calls the operating system’s synchronous getaddrinfo(3). And Promise.all fires everything before collecting, which is what makes the brute force finish in a reasonable time.

Technique 7 — dictionary attacks (the sane version)

A dictionary attack tries a list of common subdomain names instead of every combination. It is far faster and usually finds something. The book lists the top of the dnscan wordlist — www, mail, ftp, localhost, webmail, smtp, pop, ns1, webdisk, ns2, cpanel, whm, autodiscover, autoconfig, m, imap, test, ns, blog, pop3, dev, www2, admin, forum, news — and dnscan publishes 10,000 of them under a permissive licence.

Large lists should be streamed from disk rather than loaded into memory, and the same dns.resolve pattern is reused:

Streaming a wordlist and resolving each candidatebook code
const dns = require('dns');
const csv = require('csv-parser');
const fs = require('fs');
const promises = [];

fs.createReadStream('subdomains.csv')
  .pipe(csv())
  .on('data', (row) => {
    promises.push(new Promise((resolve, reject) => {
      dns.resolve(`${row.subdomain}.mega-bank.com`, function (err, ip) {
        return resolve({ subdomain: row.subdomain, ip: ip });
      });
    }));
  })
  .on('end', () => {
    // after all of the DNS queries have completed, log the results
    Promise.all(promises).then(function(results) {
      results.forEach((result) => {
        if (!!result.ip) { console.log(result); }
      });
    });
  });
The book’s recommended order

Start with the dictionary (cheap, fast, high hit rate). Only fall back to generated brute force for the strange, non-standard names the dictionary missed.

Chapter 5 · API Analysis

Once you know the hosts, the next question is: what does each host expose, with which verbs, behind which authentication, expecting which payload?

Recognising a REST API from traffic

Hierarchical resources = RESTbook code
GET  api.mega-bank.com/users/1234
GET  api.mega-bank.com/users/1234/payments
POST api.mega-bank.com/users/1234/payments

Each URL names a resource, not a function, and payments is nested inside users/1234 — so the API is hierarchical. A token on every request is the second tell, because REST is supposed to be stateless:

A stateless, token-authenticated requestbook code
POST /users/1234/payments HTTP/1.1
Host: api.mega-bank.com
Authorization: Bearer abc21323
Content-Type: application/x-www-form-urlencoded
User-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/1.0 (KHTML, like Gecko)

Which verbs does the endpoint accept?

The HTTP spec has a verb that exists purely to describe an endpoint: OPTIONS. It is the first thing to try.

Asking an endpoint what it supportsbook code
curl -i -X OPTIONS https://api.mega-bank.com/users/1234

# 200 OK
# Allow: HEAD, GET, PUT, DELETE, OPTIONS

But OPTIONS is usually enabled only on APIs deliberately published for public use, so enterprise apps rarely expose it. The practical alternative is to try each verb against a known endpoint and watch for a status code.

discoverHTTPVerbs() — try POST, GET, PUT, PATCH, DELETE on one URLbook code
const discoverHTTPVerbs = function(url) {
  const verbs = ['POST', 'GET', 'PUT', 'PATCH', 'DELETE'];
  const promises = [];

  verbs.forEach((verb) => {
    const promise = new Promise((resolve, reject) => {
      const http = new XMLHttpRequest();
      http.open(verb, url, true);
      http.setRequestHeader('Content-type', 'application/x-www-form-urlencoded');

      http.onreadystatechange = function() {
        if (http.readyState === 4) {
          return resolve({ verb: verb, status: http.status });
        }
      };

      // if the request does not complete in time, mark it as unsuccessful
      setTimeout(() => {
        return resolve({ verb: verb, status: -1 });
      }, 1000);

      http.send({});
    });
    promises.push(promise);
  });

  Promise.all(promises).then(function(values) {
    console.log(values);
  });
};

The logic is deliberately dumb: any status code at all means “this verb maps to something”; no response within a second becomes -1. One second is generous for an API, and the timeout is meant to be tuned.

Careful

Fuzzing verbs can delete or modify real data — a stray DELETE against a live endpoint is exactly as destructive as it sounds. The book requires explicit permission before doing this.

Which authentication scheme is in use?

You need to know this before you can test anything else, because most endpoints only behave interestingly for an authenticated user. The book compares the three classic schemes:

And the recognition step, in one screenshot of a request: a Basic header means basic auth, and the value decodes instantly.

Spot basic auth, then decode it in the consolebook code
GET /homepage

Because this scheme is so weak, it is normally only acceptable over TLS — which is exactly why the book notes the credentials cannot be lifted mid-air on a café Wi-Fi, but can be lifted by XSS. The recon payoff: once you know requests are authenticated with a header, re-try the endpoints that returned nothing with that header attached.

What payload shape does the endpoint expect?

  • Common shapes — many endpoints follow a public spec. An OAuth 2.0 authorisation endpoint always expects the same fields, so the spec is the documentation:
A standard OAuth 2.0 authorisation payloadbook code
{
  "response_type": code,
  "client_id": id,
  "scope": [scopes],
  "state": state,
  "redirect_uri": uri
}
  • Application-specific shapes — when no spec exists, the only reliable source is the traffic the app itself sends. Guessing works less well, and automated shape-guessing is trivially detectable.
  • Start where everyone starts — sign in, sign up, password reset. Authentication endpoints are usually built on a standard scheme, so their shapes are guessable across applications.

Chapter 6 · Identifying Third-Party Dependencies

Find the library, find the version, and an existing public exploit usually does the rest — that is what CVE databases are for.

Dependencies come in-house and external, free (open source) or licensed. They are attractive because they are often not reviewed as carefully as first-party code, and because their vulnerabilities are already public: sometimes you do not have to write an attack at all, you copy one from a CVE. These techniques apply to client-side frameworks (SPA libraries, JS helpers, CSS frameworks) and to server-side software.

Client side: SPA frameworks announce themselves

Four frameworks, four one-liners, four versionsbook code
// EmberJS — a global object with a version constant

// React — the same idea
console.log(React.version);          // 0.13.3

// VueJS — the same idea
console.log(Vue.version);            // 2.6.10

// Angular 4+ — no global version; read the attribute on the root element
const elements = getAllAngularRootElements();
const version  = elements[0].attributes['ng-version'];  // ng-version="6.1.2"
console.log(version);

Extra details the book gives per framework: Ember tags DOM elements with ember-id and wraps them in a class="ember-application" parent (usually the body). React leaves script tags of type text/jsx. Angular before 4.0 had a global angular object with angular.version; on 4.0+ you check for the ng global instead and then read ng-version. And Vue may hide its components from devtools — a single line turns them back on:

Server side: headers, error pages and fingerprints

The server is harder to see than the client, but it leaves marks.

  • Headers that talk too much — X-Powered-By: ASP.NET, or better still Server: Microsoft-IIS/4.5 plus X-AspNet-Version: 4.0.25. Competent admins remove them; millions of sites still send them.
  • Default error and 404 pages — each framework ships its own, and they survive until someone replaces them. They often reveal the framework and even a version range.

The book’s worked example is Ruby on Rails. Its default 404 page is a box saying “The page you were looking for doesn’t exist”. That page is in the public Rails repository, so its history is public too — and each commit is a timestamp marker:

DateChange to the 404 pageWhat it tells you
5 Apr 2012HTML5 type attribute removedIf type="text/css" is still there → version from 2012 or earlier
21 Nov 2013U+00A0 replaced with whitespaceIf U+00A0 is present → from Nov 2013 or earlier
20 Apr 2017Namespaced CSS selectors (.rails-default-error-page) addedIf those selectors are missing → from Apr 2017 or earlier

Combining the surviving markers with the official release schedule narrows the application to a range — in the book’s example Rails 3.2.16 to 4.2.8. And that range is vulnerable to CVE-2016-6316, an XSS where HTML padded with quotes injected into a database field is executed by an Action View tag helper. One 404 page, one version range, one documented exploit.

Server side: which database?

Database errors rarely reach the client, so the book uses a subtler signal: primary key scanning. Every database generates primary keys in its own way, so the shape of an id in traffic identifies the database.

MongoDB’s default _id is an ObjectId: exactly 12 bytes — 4 bytes of Unix timestamp, 5 random bytes, 3 bytes of a counter starting from a random value — rendered as a 12-byte hexadecimal string:

A MongoDB ObjectId, and where ids show up in trafficbook code
507f1f77bcf86cd799439011

GET users/:id                       // id in the path
PUT users, body = { id: id }        // id in the body
GET users?id=id                     // id in the query string

// …and sometimes in object metadata
{
  _id: '507f1f77bcf86cd799439011',
  username: 'joe123',
  email: 'joe123@my-email.com',
  role: 'moderator',
  biography: '...'
}

If ids look like 12-byte hex strings, you are probably looking at MongoDB. Sequential integers could be several databases, so that pattern tells you less — often you then combine it with forced error messages to disambiguate.

Chapter 7 · Identifying Weak Points in Application Architecture

One XSS is probably one careless method. Dozens of XSS in the same app is an architecture problem — and architecture is the best predictor of where the next bug will be.

First, what your map should contain

  • Technology used in the application
  • API endpoints, grouped by HTTP verb
  • API endpoint shapes, where you know them
  • Functionality included (comments, auth, notifications, uploads…)
  • Domains used by the application
  • Configurations found (e.g. a Content Security Policy)
  • Authentication and session-management systems

That list is what turns recon into prioritisation: with it you can rank what to attack first, instead of working alphabetically.

Secure vs insecure architecture, by example

Take two apps that both let users send direct messages. In the insecure one, the API accepts a script, the database stores it, nothing filters it on the way back, and it reaches the DOM — <script>alert('hacked')</script> executes. The secure one has one or more of those protections.

But per-case protections are expensive and easy to forget. The book’s framing: a secure application implements security before and during feature development; a mediocre one implements it during; an insecure one does not implement it at all. Rewrite the same messaging feature ten times over five years and each implementation will differ structurally — while the security risks stay identical.

The book’s messaging feature, reduced to its partsbook code
// client/send.js — collect the message and the target, then POST it
const send = function() {
  const message = document.querySelector('#send').value;
  const target  = document.querySelector('#target').value;
  messageUtils.sendMessageToServer(session.token, target, message);
};

// server/postMessage.js — check the request, then store it
const postMessage = function(req, res) {
  if (!req.body.token || !req.body.target || !req.body.message) {
    return res.sendStatus(400);
  }
  saveMessage(req.body.token, req.body.target, req.body.message)
    .then(() => res.sendStatus(200))
    .catch((err) => res.sendStatus(400));
};

// client/displayMessage.js — fetch a message and render it
const displayMessage = function(msgId) {
  messageUtils.getMessageById(session.token, msgId)
    .then((msg) => {
      messageUtils.appendToDOM('#message', msg);
      messageUtils.appendToDOM('#message-author', msg.author);
    })
    .catch(() => console.log('an error occured'));
};

Now the architectural fix — one shared utility, with the dangerous path explicitly labelled and off by default:

appendToDOM() — safe by default, unsafe only when askedsafe pattern
import { DOMPurify } from '../utils/DOMPurify';
// makes use of: https://github.com/cure53/DOMPurify

const appendToDOM = function(data, selector, unsafe = false) {
  const element = document.querySelector(selector);

  // for cases where DOM injection is required (not default)
  if (unsafe) {
    element.innerHTML = DOMPurify.sanitize(data);
  } else {                       // standard cases (default)
    element.innerText = data;
  }
};

Three design details matter here, and the book points them out: the flag is off by default, it is named unsafe so nobody flips it casually, and it is the last parameter, so it is unlikely to be set by accident. A utility like this is the signature of a secure architecture — and its absence is the signature of an insecure one.

Multiple layers of security

The messaging example has five places where XSS risk lives:

  • API POST
  • Database write
  • Database read
  • API GET
  • Client read

The same is true of XXE, CSRF and most other vulnerability classes. Now the failure story: the developers sanitise at API POST, so single messages are safe. A year later someone ships a bulk messaging endpoint that accepts a list of messages — and it does not reuse the same sanitisation. The original protection is bypassed without anyone touching the original code.

The lesson

An application is only as secure as the weakest link in its architecture. If defences exist at two layers (say API POST and database write), the new endpoint cannot reopen the hole. And different layers can do different things: a headless browser at the API can detect script execution, which is impossible at the database layer — but a browser-specific bug might let a payload slip past the headless browser and still execute in a vulnerable real browser. Layers complement each other precisely because they are different.

Adoption and reinvention

The last risk signal is re-inventing existing technology. It usually starts as an organisational problem and shows up in the architecture. The book’s list of reasons teams rebuild instead of adopting: avoiding complicated licences, adding functionality the existing tool lacks, marketing a new in-house feature — and the honest one, that building something from scratch is more fun and challenging than integrating someone else’s tool. Reinvention is not automatically bad; it must be evaluated case by case. But hand-rolled crypto, auth, parsers and session handling are where the worst bugs live.

Chapter 8 · Part I Summary

Recon ends when you have a map you can prioritise from — and a recorded toolkit you can automate, teach and improve.

  • Keep evolving techniques — they get stale. Server packages have become much better at not leaking their name and version, so header-based detection is worth less than it used to be.
  • Basics never disappear, technologies do — you will keep needing to map whatever is current, and you will still meet legacy stacks.
  • Record your techniques, not just your findings — a documented method can become automation, can be taught, and can be improved. Too much recon knowledge stays locked inside individual testers’ heads.
  • Share what you invent — the techniques help pen testers, and often end up improving application security for everyone.
What Part I implies for defenders

If your security depends on attackers not finding a host, an endpoint, a version or an architectural weakness, you do not have security — you have luck. Part I is a list of everything an attacker will learn about you before they send a single malicious payload; every item on it is something you can inventory, harden or remove first.
